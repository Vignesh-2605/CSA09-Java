Q3  -  ALTERNATIVE DE-DUPLICATION STRUCTURES
================================================================================================================
Name: Vignesh S   Register Number: 192325002

WHAT EACH SOLUTION LOOKS LIKE
----------------------------------------------------------------------------------------------------------------
  HashSet<Student>                 present.add(student)
     de-duplication comes from hashCode()+equals() on Student itself.

  TreeSet<Student> with Comparator  new TreeSet<>(comparing(Student::regNo))
     de-duplication comes from compare()==0.  equals() is NEVER called,
     so the class does not even need hashCode() to be correct - which is
     a trap, because the same class in a HashSet would then misbehave.

  HashMap<String,Student>           byReg.putIfAbsent(s.regNo(), s)
     de-duplication comes from the KEY, so Student needs neither equals()
     nor hashCode() at all - String already has correct ones.  This is
     the most robust of the three against a badly written entity class,
     and it keeps the first scan, which a Set does too but less visibly.

  PREDICTION: HashSet and HashMap should be indistinguishable - HashSet
  IS a HashMap with a constant value - and both O(1) average per scan.
  TreeSet should be measurably slower and should grow with n, because
  every insert walks log2(n) levels of a red-black tree comparing Strings.
  At n = 200,000 that is about 18 String comparisons per scan.

COMPLEXITY AND SPACE FOR n UNIQUE STUDENTS
----------------------------------------------------------------------------------------------------------------
STRUCTURE                    | PER SCAN         | ORDERED OUTPUT?  | SPACE PER ENTRY    | NEEDS Student.hashCode?
----------------------------------------------------------------------------------------------------------------
HashSet<Student>             | O(1) average     | no               | ~36 B (HashMap.Node) | YES - this is the trap
TreeSet<Student>+Cmp         | O(log n)         | YES, by regNo    | ~40 B (TreeMap.Entry) | no - never calls equals
HashMap<String,Student>      | O(1) average     | no               | ~36 B + key reference | no - String's is used
LinkedHashMap<String,.>      | O(1) average     | YES, by arrival  | ~44 B (+2 pointers) | no

  O(1) average, not O(1) worst case: a HashMap bucket degrades to a list
  under collisions, and Java 8+ converts a chain of 8 to a red-black tree,
  so the true worst case is O(log n) rather than O(n) - but only because
  the key's compareTo is used, which is another place a badly written
  entity class causes trouble.

RECOMMENDATION FOR THIS PROBLEM
----------------------------------------------------------------------------------------------------------------
  The fest needs a COUNT of unique students and, in practice, a register
  to print.  On that basis:

    - if only the count matters: HashSet with the corrected Student. It
      is the fastest and the most direct expression of 'a set of students'.
    - if the register must print in roll-number order: TreeSet with a
      comparator on regNo, paying O(log n) per scan to avoid an O(n log n)
      sort at the end - worth it only if the register is printed often.
    - if the entity class is outside my control, or may be changed by
      someone else later: HashMap<String,Student> keyed by regNo. It
      de-duplicates on a String, whose equals/hashCode are correct by
      definition, so the de-duplication cannot be broken by an edit to
      Student.  Experiment 1 showed how silently that edit can happen.
