1.  WHY A PLAIN Queue IS NOT SUFFICIENT
------------------------------------------------------------------------------------------------------------------------------------
  A Queue - LinkedList or ArrayDeque - is strictly FIFO: it serves in the
  order patients arrived.  The rule here is the opposite: the most severe
  patient must be seen next, whenever they arrived.  Demonstrated:

    ArrayDeque order : Ravi(S3) Meena(S1) Asha(S5) Kumar(S1)
    required order   : Meena(S1) Kumar(S1) Ravi(S3) Asha(S5)
    A critical patient is served FOURTH behind two less severe ones.

  Sorting the queue on every admission would fix the order but costs
  O(n log n) per arrival.  A PriorityQueue maintains a binary heap so
  that the minimum is always at the root: O(log n) to admit, O(log n) to
  serve, and O(1) to see who is next.

2.  HOW ARRIVAL ORDER IS PRESERVED AMONG EQUAL SEVERITIES
------------------------------------------------------------------------------------------------------------------------------------
  A PriorityQueue is NOT STABLE.  Two patients of equal severity emerge
  in whatever order the heap's sift operations happened to leave them,
  which depends on the insertion sequence and is not predictable.

  The fix is to make the ordering TOTAL rather than partial: a strictly
  increasing arrival counter is appended as a second key, so no two
  cases ever compare equal and the tie cannot be broken arbitrarily.
  A wall-clock timestamp would NOT be safe here - two admissions in the
  same millisecond would tie again - so the counter is used instead.

  Demonstration with the counter REMOVED (severity only):
    admitted A B C D E F G H, all severity 3
    served   AHGFEDCB   <- arrival order NOT preserved
    (the heap is free to return any of them first; relying on it is a bug
     even on a run where it looks correct)

  WHY PRINTING THE PriorityQueue DIRECTLY DOES NOT SHOW TREATMENT ORDER:
    toString() / iterator()  : [Meena(S1), Kumar(S1), Lata(S2), Dev(S2), Ravi(S3), John(S3), Sita(S5), Asha(S5)]
    waitingList()            : [Meena(S1), Kumar(S1), Lata(S2), Dev(S2), Ravi(S3), John(S3), Asha(S5), Sita(S5)]

  A PriorityQueue is a BINARY HEAP stored in an array.  The heap property
  guarantees only that each node is <= its two children - it says nothing
  about siblings or about the array order beyond that.  So the array is
  PARTIALLY ordered: index 0 is genuinely the next patient, and the rest
  is not a ranking at all.  Iteration walks that array, so it shows the
  heap's internal layout rather than the order of treatment.  To display
  a waiting list the contents must be copied and sorted - which is O(n
  log n) and is the cost examined in section 4.

4.  GROWTH: PREDICTED, THEN MEASURED
------------------------------------------------------------------------------------------------------------------------------------
  PREDICTION, before measuring:
    admit()        O(log n) - sift the new case up at most log2(n) levels
    next()         O(log n) - move the last element to the root, sift down
    peek()         O(1)     - read index 0
    waitingList()  O(n log n) - copy and sort

    Because log2(n) grows so slowly, going from 1,000 to 100,000 patients
    (100x) should raise the per-operation cost by only about 10/17 = 1.7x,
    NOT by 100x.  That is the prediction worth testing.
