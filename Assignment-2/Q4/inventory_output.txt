Q4  -  HashMap, TreeMap AND LinkedHashMap FOR A PHARMACY INVENTORY
======================================================================================================================
Name: Vignesh S   Register Number: 192325002
Harness: 5 warm-up runs discarded, 11 measured repetitions, MEDIAN reported.

1.  PREDICTION, DETERMINED BEFORE IMPLEMENTATION
----------------------------------------------------------------------------------------------------------------------
MAP                | put            | get            | ITERATION ORDER        | WHICH REPORT IT GIVES FREE
----------------------------------------------------------------------------------------------------------------------
HashMap            | O(1) avg       | O(1) avg       | unspecified            | neither
TreeMap            | O(log n)       | O(log n)       | sorted by key          | the CODE-ORDER report
LinkedHashMap      | O(1) avg       | O(1) avg       | insertion order        | the ARRIVAL-ORDER report

  EXTRA WORK IF THE WRONG MAP IS CHOSEN FOR A REPORT:
    HashMap       -> code-order report needs a sort of all keys: O(n log n)
                     EVERY evening, plus an O(n) copy of the key list.
    HashMap       -> arrival-order report is IMPOSSIBLE to recover at all:
                     the information was never stored.  This is the case
                     worth noticing - the other mismatches cost time, this
                     one costs correctness.
    TreeMap       -> arrival order likewise unrecoverable.
    LinkedHashMap -> code-order report needs the same O(n log n) sort.

  PREDICTED LOOKUP COST at n = 200,000: TreeMap must compare keys down
  about log2(200,000) = 17-18 levels, each a String comparison, against
  one hash and one bucket probe for the other two.  I expect TreeMap to be
  several times slower for lookups, and the gap to widen with n.
