1.  WHAT THE PRINCIPLE REQUIRES, AND WHAT IT THEREFORE FORCES
----------------------------------------------------------------------------------------------------------------------------------
  The principle names two properties: TRANSITIVITY (A>B and B>C implies
  A>C) and a WELL-DEFINED EQUALITY (equal items compare as equal).
  Together with the antisymmetry those imply, that is a TOTAL ORDER.

  Three design consequences follow directly:
    (i)   the comparison must be a FUNCTION of the items' fields only -
          anything else (insertion order, a random tiebreak, a mutable
          field) breaks transitivity the moment it changes;
    (ii)  the key sequence must END in a key that is unique, or two
          distinct items compare equal and the 'ranking' is ambiguous -
          which is why name is the final key, not an optional extra;
    (iii) the arithmetic must not overflow, because an overflowed
          subtraction flips a sign and destroys transitivity outright.

2.  Comparable OR Comparator?  THE DERIVATION
----------------------------------------------------------------------------------------------------------------------------------
QUESTION                           | Comparable<Team>                         | Comparator<Team>
----------------------------------------------------------------------------------------------------------------------------------
how many orders per type?          | exactly one                              | as many as needed
where does the rule live?          | inside the entity                        | beside the use case
can the rule change per event?     | no, it is compiled in                    | yes, pass a different one
works for a type I don't own?      | no, cannot edit the class                | yes
reusable for Player, College?      | no, each needs its own                   | yes, same chain pattern

  DECISION: Comparator, because the brief states the component will be
  reused for players, colleges and quiz teams.  Reuse across TYPES needs
  generics; reuse across ORDERINGS of the same type needs Comparator.
  Comparable would still be reasonable if a team had one permanent
  natural order - it does not.

3.  THE MULTI-FIELD COMPARISON
----------------------------------------------------------------------------------------------------------------------------------
  Comparator.comparingInt(Team::points).reversed()
            .thenComparing(comparingInt(Team::goalDiff).reversed())
            .thenComparing(Team::name);

  A detail that is easy to get wrong: .reversed() is applied to EACH
  numeric key separately, not to the whole chain.  Writing
  comparing(points).thenComparing(goalDiff).thenComparing(name).reversed()
  would reverse the NAME too, ranking Z before A among tied teams.

6.  WHY THE COMPARATOR SATISFIES THE PRINCIPLE  (by reasoning, not output)
----------------------------------------------------------------------------------------------------------------------------------
  The chain is a LEXICOGRAPHIC composition of three keys:
    k1 = -points      k2 = -goalDiff      k3 = name

  Each key maps a Team to a value in a set that already carries a total
  order: int for k1 and k2, String for k3.  comparingInt compares those
  values with < on int, which is transitive and antisymmetric by the
  definition of the integers; String.compareTo is likewise a total order
  on strings.  No subtraction is performed anywhere, so no comparison can
  overflow and no sign can flip.

  thenComparing composes them lexicographically: the result is decided by
  the first key that differs.  A lexicographic composition of total
  orders is itself a total order - if A>B and B>C, let i be the first key
  where A and B differ and j the first where B and C differ; at min(i,j)
  the comparison of A and C is decided in the same direction, because
  every earlier key is equal across all three. Transitivity follows.

  Equal items compare as equal: two Teams compare 0 exactly when points,
  goalDiff and name are all equal - which, since Team is a record whose
  equals uses those same three fields, is exactly when they are equal.
  The comparator is therefore CONSISTENT WITH equals, so the component
  behaves identically whether a List, a TreeSet or a TreeMap is used.

  exhaustively machine-checked on the test data: true
