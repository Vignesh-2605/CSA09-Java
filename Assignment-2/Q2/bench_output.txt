Q2  -  ArrayList, LinkedList AND ArrayDeque FOR A PLAYLIST EDITOR
======================================================================================================================
Name: Vignesh S   Register Number: 192325002
Harness: 5 warm-up runs discarded, 11 measured repetitions, MEDIAN reported.

1.  PREDICTION  (recorded before any measurement)
----------------------------------------------------------------------------------------------------------------------
OPERATION                | ArrayList        | LinkedList       | ArrayDeque       | WHY
----------------------------------------------------------------------------------------------------------------------
add at end               | O(1) amortised   | O(1)             | O(1) amortised   | array doubling is rare; node alloc is constant
insert at front          | O(n)             | O(1)             | O(1)             | array must shift every element right
insert in middle         | O(n) shift       | O(n) walk        | not supported    | both O(n), but a shift is far cheaper than a walk
get k-th                 | O(1)             | O(n)             | no index API     | one array index vs following k references
iterate all              | O(n), cache-friendly | O(n), pointer chase | O(n)             | array is contiguous; nodes are scattered
remove from front        | O(n)             | O(1)             | O(1)             | same shifting cost as inserting at the front

  The prediction worth testing is NOT the Big-O - that is textbook - but
  the claim hidden inside it: that LinkedList's O(1) front insert actually
  beats ArrayList's O(n) shift in practice.  System.arraycopy moves a
  contiguous block at memory-bandwidth speed, while allocating a node
  costs a heap allocation and a cache miss.  I expect ArrayList to win on
  small playlists despite being asymptotically worse, with LinkedList
  overtaking it only once n is large.  Finding that crossover is the
  point of the experiment.
