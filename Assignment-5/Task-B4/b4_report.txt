3.  THE EXPANDED SYSTEM: 12 CAMPUSES, 100x THE PASSES
----------------------------------------------------------------------------------------------------------------------
  today      : about 8,000 passes a year, one office
  expanded   : about 800,000 passes a year, 12 campuses issuing at once

  REQUIREMENT                | TEXT FILE              | SERIALIZATION          | DATABASE
  --------------------------------------------------------------------------------------------------------------
  find one pass by ID        | O(n) scan - measured 35 ms at 100,000 | load the whole graph first | O(log n) on the primary key
  12 counters writing at once | file corruption - no locking | whole-file rewrite each time | row locks and transactions
  a failed half-write        | a torn last line       | the whole file is unreadable | rolled back - measured in B3
  search by route            | O(n) scan              | O(n) in memory         | an index, O(log n)
  adding a phone column      | every reader must change | breaks old files, see A4 | ALTER TABLE, old code unaffected
  who changed what           | nothing                | nothing                | timestamps, audit tables
  memory to serve a query    | one 8 kB buffer        | the entire object graph | whatever one page needs
  concurrent read while writing | may read a half-written line | not possible           | isolation levels

  DECISION: a DATABASE, and the measurements in this assignment are why.

    Searching.  B1 measured a text-file search at about 35 ms per lookup
    over 100,000 records, and that is O(n): at 800,000 it is roughly
    280 ms for ONE counter query. The HashMap alternative fixes the
    lookup but costs about 39 MB for 100,000 passes and has to be
    rebuilt in every process - 12 campuses means 12 copies, each stale
    the moment another campus issues a pass.

    Concurrent counters.  This is the requirement that settles it. A
    text file has no way for 12 processes to append safely, and a
    serialized file is rewritten whole, so two campuses saving at once
    lose one of the two. The database was built for exactly this.

    Safety.  B3 showed 499 orphan rows left behind by an auto-commit
    import that failed halfway, and zero left behind by the same import
    inside one transaction. Neither file format offers rollback at all.

    Loading speed is NOT the reason. B3 measured 100,000 rows inserted
    in about 2.7 seconds by batch - fast enough, but a text file would
    append them faster. Speed of writing is the one contest the files
    win, and it is the least important requirement on the list.

4.  ONE SHARED DATABASE, OR ONE SERIALIZED FILE PER CAMPUS?
----------------------------------------------------------------------------------------------------------------------
                                 | 12 SERIALIZED FILES              | ONE SHARED DATABASE
  --------------------------------------------------------------------------------------------------------------
  a student at two campuses      | invisible - no file knows        | one UNIQUE constraint
  total passes issued            | open and merge 12 files          | one COUNT query
  one campus offline             | its file is simply missing       | its rows are still there
  schema change                  | 12 files to migrate, see A4      | one ALTER TABLE
  a campus-local query           | fast - its own file only         | indexed, still fast
  failure blast radius           | one campus                       | all 12 - the honest cost
  backup                         | 12 files to keep in step         | one consistent backup

  One shared database, with a campus_id column. The deciding row is the
  first: a transport office that cannot tell whether a student already
  holds a pass at another campus cannot enforce its own rule, and no
  arrangement of 12 separate files fixes that without rebuilding the
  thing a database already is.

  The honest cost is row 6: one shared database is one thing to lose.
  That is answered with backups and replication, not by splitting the
  data into 12 files that cannot answer the first question.
