TASK 8  -  POLYMORPHISM
================================================================================

1.  COMPILE-TIME POLYMORPHISM: OVERLOADED calculateFee
--------------------------------------------------------------------------------
  three overloads exist:
     calculateFee(int)                  minutes already known
     calculateFee(long)                 a wider integral duration
     calculateFee(LocalTime, LocalTime) clock times at the barriers

  a) calculateFee(130)              - argument is an int literal
            >> body that ran: Car.ratePerHour() -> 30
     -> Rs 90   compiler chose calculateFee(int): exact match

  b) calculateFee(130L)             - argument is a long literal
            >> body that ran: Car.ratePerHour() -> 30
     -> Rs 90   compiler chose calculateFee(long): exact match,
        no narrowing is ever applied implicitly

  c) calculateFee(LocalTime.of(9,0), LocalTime.of(11,10))
            >> body that ran: Car.ratePerHour() -> 30
     -> Rs 90   two arguments, so only one overload is applicable

  d) calculateFee(shortValue)       - argument is a short
            >> body that ran: Car.ratePerHour() -> 30
     -> Rs 90   short WIDENS to int; the compiler prefers the
        narrowest applicable widening, so calculateFee(int) wins over
        calculateFee(long)

  HOW THE COMPILER SELECTS: it fixes the method at COMPILE time from the
  static types of the arguments, in three phases - exact match first,
  then widening, then boxing/varargs - and if two are equally specific it
  is an ambiguity ERROR, not a runtime choice.  The object's real class
  plays no part in this decision at all.

2.  UPCASTING: ONE ARRAY OF Vehicle HOLDING THREE DIFFERENT TYPES
--------------------------------------------------------------------------------
  Vehicle[] parked = { new TwoWheeler(..), new Car(..), new ElectricCar(..) };

  INDEX      | DECLARED TYPE  | ACTUAL CLASS   | ASSIGNMENT NEEDED
  ----------------------------------------------------------------------------
  0          | Vehicle        | TwoWheeler     | none - upcast is implicit
  1          | Vehicle        | Car            | none - upcast is implicit
  2          | Vehicle        | ElectricCar    | none - upcast is implicit

  The upcast is implicit and always safe, because every element really
  IS-A Vehicle.  The array's element type is the CONTRACT (anything that
  can be parked and billed), not the implementation.

3.  RUNTIME POLYMORPHISM: DYNAMIC METHOD DISPATCH, TRACED
--------------------------------------------------------------------------------
  one line of source is executed three times:
      long fee = v.calculateFee(130);

    iteration with element TwoWheeler TN01AB1111
        declared type of v   : Vehicle          (fixed at compile time)
        actual object type   : TwoWheeler       (discovered at run time)
        method invoked       : Vehicle.calculateFee(int)  [final-style,
                               not overridden - one billing rule]
        which calls          : ratePerHour()  -> DISPATCHED
            >> body that ran: TwoWheeler.ratePerHour() -> 10
        fee                  : Rs 30

    iteration with element Car TN02CD2222
        declared type of v   : Vehicle          (fixed at compile time)
        actual object type   : Car              (discovered at run time)
        method invoked       : Vehicle.calculateFee(int)  [final-style,
                               not overridden - one billing rule]
        which calls          : ratePerHour()  -> DISPATCHED
            >> body that ran: Car.ratePerHour() -> 30
        fee                  : Rs 90

    iteration with element ElectricCar TN03EF3333
        declared type of v   : Vehicle          (fixed at compile time)
        actual object type   : ElectricCar      (discovered at run time)
        method invoked       : Vehicle.calculateFee(int)  [final-style,
                               not overridden - one billing rule]
        which calls          : ratePerHour()  -> DISPATCHED
            >> body that ran: Car.ratePerHour() -> 30
        fee                  : Rs 210 + charging 10 kWh
                               (ElectricCar inherits Car's rate: an
                               EV parks at the car tariff by design)

  THE MECHANISM: calculateFee() is resolved at compile time to
  Vehicle.calculateFee(int), but the ratePerHour() call inside it is
  compiled to invokevirtual.  At run time the JVM reads the object's
  header, finds its class, looks ratePerHour() up in that class's method
  table and jumps there.  The DECLARED type decides what may be called;
  the ACTUAL type decides which body runs.

4.  WHY THIS AVOIDS A LONG if-else CHAIN ON THE VEHICLE TYPE
--------------------------------------------------------------------------------
  the chain that dispatch replaces:
      if (v instanceof ElectricCar)  return hours * 30;
      else if (v instanceof Car)     return hours * 30;
      else if (v instanceof TwoWheeler) return hours * 10;
      else throw new IllegalArgumentException(...);

  VEHICLE            | dispatch       | if-else chain  | AGREE?
  ----------------------------------------------------------------------
  (dispatch call for TwoWheeler)
            >> body that ran: TwoWheeler.ratePerHour() -> 10
  TN01AB1111         | Rs 30          | Rs 30          | yes
  (dispatch call for Car)
            >> body that ran: Car.ratePerHour() -> 30
  TN02CD2222         | Rs 90          | Rs 90          | yes
  (dispatch call for ElectricCar)
            >> body that ran: Car.ratePerHour() -> 30
  TN03EF3333         | Rs 90          | Rs 90          | yes

  Both give the same answer today.  The chain is still the worse design:
   - ORDER MATTERS.  ElectricCar must be tested BEFORE Car, because an
     ElectricCar IS-A Car and the Car branch would otherwise swallow it.
     Reordering two lines silently changes the bill.
   - It lives OUTSIDE the classes, so adding a type means editing a
     method that already works and was already tested.
   - The final else is reachable, so 'unknown vehicle type' is a runtime
     error the compiler cannot warn about.  With dispatch that branch
     does not exist, because an unimplemented abstract method is a
     compile error instead.

  Quantified in InstanceofComparison.java in this folder: the chain costs
  up to k tests for k vehicle types, dispatch costs one indirect jump.
