TASK 7  -  OVERRIDING AND SPECIALISING BEHAVIOUR
================================================================================

1.  WHICH METHODS ARE OVERRIDDEN, AND WHY
--------------------------------------------------------------------------------
METHOD             | OVERRIDDEN IN    | WHY THE SUBCLASS VERSION IS NEEDED
--------------------------------------------------------------------------------
ratePerHour()      | every subclass   | the tariff genuinely differs per type
toString()         | Vehicle, ElectricCar | a ticket must print readably
equals()           | Vehicle          | identity is the plate, not the address
hashCode()         | Vehicle          | must stay consistent with equals()
calculateFee()     | NOBODY - it is final | the billing rule must not vary

2.  THE RULES OF OVERRIDING THAT @Override ENFORCES
--------------------------------------------------------------------------------
  signature    : name and parameter list must match EXACTLY.
                 double ratePerHour(int) would be an OVERLOAD, not an
                 override - and the abstract method would stay unimplemented.
  return type  : identical, or a subtype (covariant return).
  access       : may widen (protected -> public) but never narrow.
                 protected -> private does not compile.
  exceptions   : no NEW or BROADER checked exception may be declared.
  static/final : a static method is hidden, not overridden; a final
                 method cannot be overridden at all.

  @Override itself changes no behaviour - it asks the COMPILER to check
  that a supertype method really is being replaced.  Without it, a typo
  such as 'ratePerHor()' would compile as a brand-new method and the
  object would silently keep the inherited rate.  See the commented
  experiment at the bottom of this file.

3.  WHERE final IS APPROPRIATE, AND WHY
--------------------------------------------------------------------------------
DECLARATION                | KIND         | REASON
--------------------------------------------------------------------------------
private final String regNo | variable     | identity must not change after equals()
static final MINUTES_PER_HOUR | constant     | a unit conversion is not configurable
public final calculateFee() | method       | the billing RULE is fixed; only the rate varies
final class ElectricCar    | class        | closes the branch; no hidden re-specialisation

  The final on calculateFee() is the important one.  It is what makes the
  design safe: a subclass can change WHAT IT COSTS per hour, but it can
  never change the rule that a part-hour is charged as a whole hour, so
  no future vehicle type can quietly under-bill the campus.

4.  OVERRIDDEN ratePerHour() SEEN THROUGH A SUPERCLASS REFERENCE
--------------------------------------------------------------------------------
ACTUAL CLASS   | RATE/HR   | FEE 130 min | toString()
--------------------------------------------------------------------------------
TwoWheeler     | Rs 10     | Rs 30       | TwoWheeler[TN01AB1111, Rs 10/hr]

5.  equals(), hashCode() AND toString() WORKING TOGETHER
--------------------------------------------------------------------------------
carA == carB  (reference identity)             | false
carA.equals(carB)  (same plate, same class)    | true
carA.equals(evSame)  (same plate, SUBCLASS)    | true
carA.equals(other)  (different plate)          | false
carA.hashCode() == carB.hashCode()             | true
carA.hashCode() == evSame.hashCode()           | true

  Why instanceof Vehicle and not getClass() == o.getClass():
  one physical car has ONE number plate.  If the same plate were
  registered once as a Car and once as an ElectricCar, they are still
  the same vehicle and the facility must refuse the duplicate entry.
  A getClass() comparison would call them different and let the vehicle
  occupy two slots at once.  The cost of this choice is that equals()
  is no longer symmetric with a subclass that adds its own equality
  fields - which is precisely why ElectricCar is declared final.

6.  THE CONSEQUENCE FOR HashSet AND HashMap
--------------------------------------------------------------------------------
  add(carA)   -> true   (new vehicle admitted)
  add(carB)   -> false   (same plate: REFUSED as a duplicate)
  add(evSame) -> false   (same plate: REFUSED as a duplicate)
  add(other)  -> true   (different plate admitted)
  vehicles recorded inside = 2  (expected 2)

  entryMinute.put(carA, 540)
  entryMinute.get(carB)   -> 540   (found with a DIFFERENT object, same plate)
  entryMinute.get(evSame) -> 540   (found across the subclass too)

  This is the whole point of overriding hashCode() alongside equals():
  the exit barrier can look a vehicle up from a freshly scanned plate
  without holding the original object.  Had hashCode() been left as
  Object's identity hash, get(carB) would return null and every vehicle
  would be unable to leave.
