## 1.1 Inputs the system receives and outputs it must produce

| Direction | Item | Type |
|---|---|---|
| Input | registration number | `String` |
| Input | vehicle type | two-wheeler / car / EV |
| Input | user category and pass status | enum + `Pass` |
| Input | entry time, exit time | minutes from midnight |
| Input | facility layout | slots per floor |
| Input | units drawn at a charging slot | `int` kWh |
| Output | allocated floor and slot | `(floor, slot)` |
| Output | ticket number | unique `int` |
| Output | duration of stay | whole minutes |
| Output | payable fee | whole rupees |
| Output | refusal | when full, or when the input is invalid |

## 1.2 Nouns that become classes, verbs that become methods

Reading the problem statement and underlining its nouns gives the candidate
classes; the verbs give the operations.

| Candidate class | From the noun | Responsibility | Why it must exist |
|---|---|---|---|
| `ParkingFacility` | *facility* | owns the floors and slots, runs entry and exit | something must hold the invariant "one vehicle per slot" across the whole building; no smaller object can see all the slots |
| `Slot` | *numbered slot* | knows its position and its single occupant | occupancy is a property of a *place*, and the rule "a slot cannot hold two vehicles" has to live with the thing it constrains |
| `Vehicle` | *vehicle, two-wheeler, car, EV* | identity and tariff | the fee differs by type, so type must be a first-class thing rather than a string tested in an `if` |
| `ParkingTicket` | *parking ticket* | unique number, slot, entry time | the stay is an entity in its own right: it outlives neither the vehicle nor the slot, and the fee is computed from exactly its fields |
| `CampusUser` | *students, staff, visitors* | category and pass; decides whether a fee is due | "who pays" is a rule about the *owner*, not about the vehicle, and putting it on `Vehicle` would make a staff car a different *kind* of car |

| Verb in the problem | Method |
|---|---|
| "a vehicle enters ... allocate a suitable free slot" | `ParkingFacility.admit(Vehicle, CampusUser, int)` |
| "issue a parking ticket with a unique ticket number" | `new ParkingTicket(...)` using a class-wide counter |
| "when the vehicle leaves ... release the slot" | `ParkingFacility.release(...)` |
| "compute the parking fee" | `Vehicle.calculateFee(int)` |

**Why each class is needed, not merely listed.** The test applied was: *remove
this class and ask which rule becomes unenforceable.* Remove `Slot` and
occupancy becomes a bare `String[][]`, so "a slot cannot hold two vehicles"
degrades to a convention that any caller may break. Remove `ParkingTicket` and
the entry time has nowhere to live between entry and exit. Remove `CampusUser`
and the pass rule has to be re-tested at every exit. Each class survives the
test; nothing else proposed did - a `Floor` class, for example, was rejected
because a floor has no behaviour of its own beyond being a row of slots, and
`slots[f].length` already carries everything a floor knows.

## 1.3 Business rules every valid operation must satisfy

| # | Rule | Where it is enforced | Demonstrated |
|---|---|---|---|
| 1 | a slot cannot hold two vehicles | `Slot.occupy()` | REJECTED in output |
| 2 | a ticket number is never reused | `static` counter, `++` on construction | numbers 1001, 1002, 1003 |
| 3 | the same vehicle cannot be inside twice | `Facility.admit()` | REJECTED in output |
| 4 | a registration number is mandatory | `VehicleRecord` constructor | REJECTED in output |
| 5 | a slot is released only against an issued ticket | `Facility.release()` | REJECTED in output |
| 6 | entry is refused when nothing is free | `admit()` returns `null` | "REFUSED, facility is full" |
| 7 | a staff or student pass exempts the fee; a visitor always pays | `CampusUser.paysFee()` | table in output |

The program does not merely state these rules - it **violates each one on
purpose** and shows the guard firing, which is why the output contains lines
such as `Rule 1 violated: slot 0/0 already holds TN01AB1111`.

## 1.4 Assumptions

1. Slot numbering starts at 0 on every floor and is contiguous.
2. Any vehicle type fits any slot in the base design; Task 12 adds typed slots.
3. Time is whole minutes from midnight, so no date arithmetic is needed; a stay
   that crosses midnight is handled by wrapping, not by a calendar.
4. A monthly pass is valid for the whole stay; expiry is not checked in the base
   design. Task 12 removes this assumption.
5. One gate operator acts at a time, so the model is single-threaded.

## 1.5 Alternative Concept and Complexity Analysis

> *If the vehicles were stored as plain Strings in parallel arrays
> `regNo[]`, `type[]`, `entryTime[]`, what would the solution look like?*

**Evidence:** `Task01/ParallelArraysComparison.java`, `Task01/alt_output.txt`

Both designs were implemented and measured with n = 200,000 records and 2,000
probes including deliberate misses.

| Design | Finding a vehicle | Complexity | Adding an attribute | Risk |
|---|---|---|---|---|
| A - array of objects | linear scan | **O(n)** | one field in one class | none; the compiler checks it |
| B - parallel String arrays | linear scan | **O(n)** | a 4th array **plus every loop** | the arrays silently fall out of step |

The measured per-probe times came out within noise of one another - around
400 µs each - which is the honest result: **neither design makes the search
faster.** Both scan linearly, so the complexity is identical and speed decides
nothing.

| Design | Space per vehicle |
|---|---|
| A - objects | 1 reference + 1 object header (≈16 B) + 2 references + 1 `int` |
| B - parallel arrays | 3 references, no per-vehicle header |

Design B saves roughly one object header per vehicle - about 3 MB at
n = 200,000.

**Decision: the object design is retained.** The argument is correctness, not
speed. A `ParkedVehicle` object keeps the invariant that *one vehicle is one
thing*: three facts about the same car cannot drift apart, because they are not
three arrays. Parallel arrays also cannot express a type hierarchy at all, so
they foreclose `calculateFee()` as an overridden method (Tasks 7-8) before the
design has begun. The 3 MB is the price of that, and it is worth paying.

# TASK 2 - Choose the Data Representation  *(3 marks, K4)*

**Evidence:** `Task02/DataRepresentationDemo.java`, `Task02/ScannerInputDemo.java`,
`Task02/actual_output.txt`, `Task02/scanner_output.txt`

## 2.1 Data type for each field

| Field | Type | Why this type |
|---|---|---|
| slot number | `int` | a small whole count, used directly as an array index; no fractional slot exists |
| floor number | `int` | as above |
| vehicle number | `String` | letters and digits; compared with `equals()`, never `==` |
| entry / exit time | `int` minutes from midnight (`LocalTime` at the boundary) | arithmetic on minutes is exact; a calendar type at the UI edge keeps display correct |
| duration | `int` | whole minutes; a day is 1,440, so overflow is impossible |
| **fee** | **`long`** | **whole rupees; money is never held in `double`** |
| occupancy | `boolean` / `null` `String` | a slot is free or it is not |

Money is `long` and never `double`: a binary floating-point type cannot
represent one rupee exactly in all cases, and a cumulative day total would
accrue error. Keeping the fee integral also means the entire money path can be
computed with integer arithmetic, so no rounding mode has to be chosen.

## 2.2 Floors and slots: a jagged array

```java
String[][] slots = new String[floors][];       // rows sized individually
for (int f = 0; f < floors; f++)
    slots[f] = new String[slotsPerFloor[f]];
```

For the real facility `{20, 50, 50, 100, 100}` - 320 slots:

| Representation | Cells allocated | Consequence |
|---|---|---|
| **jagged `String[f][]`** | **320** | exact fit; `slots[f].length` *is* the floor's size |
| rectangular `String[5][100]` | 500 | 180 cells wasted, and every loop needs a second `validSlots[]` array |

The jagged form is chosen because the ragged floor sizes become part of the
structure. There is no second array to keep in step: the bound the allocation
loop needs is `slots[f].length`, which cannot disagree with the array it
describes. Task 12 then extends the facility to 5 floors of 20/50/50/80/12 and
this choice absorbs the change with **no code modification at all** - the
constructor is simply handed a longer `int[]`.

## 2.3 Where casting is required, and the risk of losing precision

The conversion from minutes to billable hours is the one place a cast could
destroy money. The rule is *every started hour is charged in full*, and the
program demonstrates two wrong implementations against the correct one:

| Minutes | `minutes / 60` | `(int)(minutes / 60.0)` | **Correct** | Loss |
|---|---|---|---|---|
| 1 | Rs 0 | Rs 0 | **Rs 30** | Rs 30 |
| 59 | Rs 0 | Rs 0 | **Rs 30** | Rs 30 |
| 60 | Rs 30 | Rs 30 | Rs 30 | - |
| 61 | Rs 30 | Rs 30 | **Rs 60** | Rs 30 |
| 130 | Rs 60 | Rs 60 | **Rs 90** | Rs 30 |
| 185 | Rs 90 | Rs 90 | **Rs 120** | Rs 30 |

Over these nine sample stays the truncating versions under-charge by **Rs 180**.
The failure is worst at the low end: *a one-minute stay bills Rs 0*, so the
facility would earn nothing from any vehicle staying under an hour.

**How the design avoids it:**

```java
int billableHours = (minutes + 59) / 60;    // integer ceiling
```

Adding 59 pushes any non-zero remainder up into the next whole hour, so the
division rounds **up** while remaining pure integer arithmetic. No `double` is
created, so no rounding error can enter the money path. The result is held in
`long` because `int` rupees could overflow on a long-stay or season total.

Boundary verification from the run: 0 min → Rs 0; 1 min → Rs 30; 60 min →
Rs 30; 61 min → Rs 60; -5 min → **REJECTED**.

**`Scanner`** for the interactive gate console, because the operator types one

because those are fixed before the program starts and make a run reproducible.

`ScannerInputDemo` reads from `input.txt` and shows `hasNextInt()` checked

## 2.5 Alternative Concept and Complexity Analysis

> *Instead of a jagged array, suppose the slots are stored in a single 1-D array
> using `index = floor × slotsPerFloor + slot`, or in an `ArrayList<String[]>`.*

**Evidence:** `Task02/SlotStorageComparison.java`, `Task02/alt_output.txt`

| Representation | Cells for {20,50,50,100,100} | Consequence |
|---|---|---|
| A - jagged `String[f][]` | 320 | exact fit; length per floor is free |
| B - flat, uniform stride | 500 | wastes 180 cells **and the index is wrong** |
| B' - flat + prefix sums | 320 | exact fit, but needs 6 extra `int`s |
| C - `ArrayList<String[]>` | 320 | exact fit; floors can be added at run time |

**What breaks with ragged floors.** The single stride is fatal. With floor sizes
20/50/50/100/100 there is no one value of `slotsPerFloor` that works:

* `index = floor × 100 + slot` leaves 80 dead cells on floor 0;
* `index = floor × 20 + slot` makes floor 1 slot 25 **collide** with floor 2
  slot 5 - two different vehicles mapping to one cell.

The flat form survives only by carrying a prefix-sum array `start[]`, which is
the floor lengths written out a second time by hand - precisely the information
`slots[floor].length` already provides for free.

**Time and space.** All four locate a slot in **O(1)**, and the measured
per-read times (≈2 ns) are within noise of one another. Speed decides nothing.
Space: A uses 320 references + 5 row headers; B wastes 180 references; B' needs
6 extra `int`s; C adds a list object and backing array.

**Decision: the jagged array is retained**, because it is the only form that
stores the ragged floor sizes *as part of the structure*, so no second array can
fall out of step with it. `ArrayList<String[]>` would be correct if floors had
to be added while the program runs, which this requirement does not ask for.

# TASK 3 - Design the Control Logic  *(4 marks, K4)*

**Evidence:** `Task03/ParkingFacility.java` (Complete the Code),
`Task03/FeeSlabLogic.java`, `Task03/PSEUDOCODE.md`,
`Task03/screenshots/01-parking-facility.png`

## 3.1 Pseudocode (SIMATS Engineering standard form)

Full pseudocode for both operations, with pre- and post-conditions, termination
arguments and a step-by-step trace, is in **`Task03/PSEUDOCODE.md`**. The
essentials:

```
ALGORITHM   ALLOCATE_SLOT
INPUT       slots[0..F-1][...], F, vehicleNo
OUTPUT      (floor, slot) occupied, or NULL if none was free
BEGIN
 1.  FOR floor <- 0 TO F - 1 DO
 2.      S <- LENGTH(slots[floor])          // each floor carries its own size
 3.      FOR slot <- 0 TO S - 1 DO
 4.          IF slots[floor][slot] = NULL THEN
 5.              slots[floor][slot] <- vehicleNo
 6.              RETURN (floor, slot)        // stops both loops at once
 7.          END IF
 8.      END FOR
 9.  END FOR
10.  RETURN NULL                             // every slot is taken
END
```

```
ALGORITHM   COMPUTE_FEE
INPUT       entryMinute, exitMinute, vehicleType, user
OUTPUT      fee, whole rupees, 0 <= fee <= DAILY_CAP(vehicleType)
BEGIN
 1.  duration <- exitMinute - entryMinute
 2.  IF duration < 0 THEN RAISE InvalidDuration END IF
 5.  IF duration = 0 THEN RETURN 0 END IF            // drive-through
 9.  IF user HAS a valid pass AND user.category <> VISITOR THEN RETURN 0 END IF
13.  billableHours <- CEILING_DIV(duration, 60)      // (d + 59) DIV 60
14.  rate <- BASE_RATE(vehicleType)
15.  IF billableHours = 1 THEN fee <- rate
18.  ELSE fee <- rate + (billableHours - 1) * rate END IF
21.  IF fee > DAILY_CAP(vehicleType) THEN fee <- DAILY_CAP(vehicleType) END IF
24.  IF vehicleType = EV AND charging used THEN fee <- fee + CHARGE_RATE * kWh END IF
27.  RETURN fee
END
```

`ALLOCATE_SLOT` is **O(F × S)** worst case, **O(1)** best case, **O(1)** extra
space. `COMPUTE_FEE` has no loop: **O(1)** time and space.

## 3.2 How the search runs and when it stops

The outer loop walks floors from 0 upward; the inner loop walks slots from 0
upward; the search stops at the **first** free cell. The ordering is a policy
decision, not an accident: filling the lowest floor first keeps vehicles near
the entrance and means the upper floors are untouched when the facility is
lightly used.

## 3.3 Fee slabs: `if-else` and `switch`, compared

Both formulations were implemented and run against 30 cases (3 vehicle types ×
10 durations). **Every case agrees.**

`if-else` is kept in the final design, because the slab boundaries are
**ranges** - `hours > 1`, `fee > cap` - and `switch` can only test equality of
a single value. The `switch` version has to compute the hour count first and
*still* falls through to a `Math.min` for the cap, so it is strictly longer
without being clearer.

## 3.4 How `break`, `continue` and `return` avoid work

| Keyword | What it saves |
|---|---|
| `return` | ends the search the instant a slot is taken, so a vehicle never reads a cell beyond the one it occupies |
| `break` | stops re-reading a floor once it is proved full |
| `continue` | skips a known-full floor entirely on every later call |

Measured on a 9-slot facility `{3, 2, 4}`:

| Call | Result | Cells read | Floors skipped |
|---|---|---|---|
| 1 | [0, 0] | 1 | - |
| 4 | [1, 0] | 4 | 1 known-full |
| 5 | [1, 1] | **2** | 1 known-full |
| 8 | [2, 2] | 3 | 2 known-full |
| 10 | FULL, refused | 4 | 3 known-full |

Without `continue`, call 10 would read all 9 cells. With it, the cell count stays
small as the facility fills.

## 3.5 What happens when no suitable slot is free

`allocate()` returns `null`, and the caller **must refuse entry rather than
issue a ticket**. No ticket is created, no slot is written and the counter is
not advanced, so a refused vehicle leaves the system in exactly the state it
found it. Test `B5` in Task 11 verifies precisely that.

## 3.6 Complete the Code - `ParkingFacility`

Both `TODO`s completed; `main()` untouched.

```java
public int[] allocate(String vehicleNo) {
    for (int f = 0; f < slots.length; f++)
        for (int s = 0; s < slots[f].length; s++)
            if (slots[f][s] == null) { slots[f][s] = vehicleNo; return new int[]{f, s}; }
    return null;
}

public boolean release(int floor, int slot) {
    if (floor < 0 || floor >= slots.length) return false;
    if (slot < 0 || slot >= slots[floor].length) return false;
    if (slots[floor][slot] == null) return false;
    slots[floor][slot] = null;
    return true;
}
```

| | Output |
|---|---|
| **Expected** | `[0, 0]` `[0, 1]` `[1, 0]` `null` `true false false` `[0, 1]` |
| **Actual** | `[0, 0]` `[0, 1]` `[1, 0]` `null` `true false false` `[0, 1]` |

`diff actual_output.txt expected_output.txt` → **identical**.

The three results of the `release` line are each a different guard: `true` frees
an occupied slot, the second `false` rejects a slot that is already free, and
`release(5, 0)` rejects a floor that does not exist.

## 3.7 Alternative Concept and Complexity Analysis

> *If a count of free slots per floor and a stack of free slot numbers were
> maintained, what would `allocate()` and `release()` become?*

**Evidence:** `Task03/FastAllocator.java`, `Task03/alt_output.txt`

Measured on a 5 × 100 facility, 4,000 release+allocate pairs on the **last**
slot - the worst case for scanning:

| Design | Total (ms) | Per pair (µs) | Cells read |
|---|---|---|---|
| A - scanning | 9.32 | 2.331 | 2,000,000 |
| B - free-count + stack | **1.27** | **0.317** | **20,000** |
| | | **7.4× faster** | **100× fewer reads** |

| Operation | A scanning | B count + stack |
|---|---|---|
| `allocate()` worst case | **O(F × S)** | **O(F)** |
| `allocate()` best case | O(1) | O(1) |
| `release()` | O(1) | O(1) |

Extra space for B: `int[F][S] + int[F]` = 2,020 bytes for 5 × 100 - i.e. one
extra `int` per slot, **O(F × S)**.

**Decision.** B is strictly faster and is the right structure for a large, busy
facility. A is kept in *this* submission for a specific reason: the required
`main()` fixes the allocation **order** - the first free slot, scanning floor by
floor - while a LIFO stack hands back the most recently freed slot. The stack is
therefore the correct optimisation to adopt the moment the allocation order is
free to change, and Task 12 records it as the extension point.

# TASK 4 - Design Classes, Objects and Constructors  *(4 marks, K4)*

**Evidence:** `Task04/ConstructorDemo.java`, `Task04/actual_output.txt`

## 4.1 Fields and methods

`ParkingTicket` holds `ticketNo`, `vehicleNo`, `floor`, `slot`, `entryMinute`
(all `final`), a mutable `exitMinute`, a `duplicate` flag, and a `static`
`lastTicketNo`. Every field is `private`; the only mutator is `close(int)`,
which validates that the exit does not precede the entry.

## 4.2 The four constructors, and when each is used

| # | Constructor | Used when |
|---|---|---|
| 1 | `ParkingTicket(String, int, int, int)` | the full case: every fact is known at the gate |
| 2 | `ParkingTicket(String, int, int)` | slot known, entry time defaults to 09:00 |
| 3 | `ParkingTicket(String)` | a walk-in whose slot is assigned later |
| 4 | `ParkingTicket(ParkingTicket)` | **copy constructor** - re-issuing a lost ticket |

## 4.3 `this` and constructor chaining

```java
ParkingTicket(String vehicleNo, int floor, int slot) {
    this(vehicleNo, floor, slot, 9 * 60);   // delegates; no repeated checks
}
```

`this` is used two ways: to disambiguate a field from a same-named parameter
(`this.vehicleNo = vehicleNo`), and as `this(...)` to delegate to the full
constructor. The short constructors perform **no validation of their own** -
the three guard clauses live in exactly one place.

The captured trace proves the delegation order, because the full constructor
prints first in every case:

```
  b) overloaded 3-arg ...
      [full constructor ran for TN02CD2222]
      [3-arg constructor chained to the full one]
```

`this(...)` must be the first statement in a constructor body, which is why the
parent finishes before the delegating constructor's own body runs. That the
shared validation still protects the short forms is shown by `negative floor →
REJECTED: floor and slot cannot be negative` raised from a *3-argument* call.

## 4.4 Is a copy constructor needed? Yes - and why

A driver who loses the printed ticket needs a duplicate that carries the **same
stay** (so the fee is unchanged) but a **different ticket number** (so rule 2
holds and the original cannot be presented again).

| Property | Original | Re-issued |
|---|---|---|
| vehicle | TN01AB1111 | TN01AB1111 - same |
| entry time | 540 | 540 - same |
| ticket number | 1001 | **1004 - different** |
| marked duplicate | false | **true** |

A plain assignment would not do this: `ParkingTicket alias = t1;` gives
`alias == t1 → true`, i.e. **one object with two names**, not a copy.

## 4.5 How objects are stored in memory

`t1`, `t2`, `t3`, `t4` and `alias` are **reference variables** in `main()`'s
stack frame. The `ParkingTicket` **objects** are on the heap. `alias` and `t1`
hold the same address, so there are **4 objects on the heap but 5 references on
the stack**:

```
 stack (main)              heap
 t1    ----------------->  [Ticket#1001 TN01AB1111]  <--- alias
 t2    ----------------->  [Ticket#1002 TN02CD2222]
 t3    ----------------->  [Ticket#1003 TN03EF3333]
 t4    ----------------->  [Ticket#1004 TN01AB1111 DUP]
```

`static lastTicketNo` is in neither place - it belongs to the class and lives in
the method area, one copy however many tickets exist.

**Passing and returning.** Java passes the **value of the reference**:
`closeIt(t2)` changes the object through the shared address, but `repoint(t2)`
rebinds only its own local copy, so `main()`'s `t2` is unchanged (ticket number
still 1002 after the call). This is why the facility *returns* a new
`ParkingTicket` rather than filling in one the caller passed down.

## 4.6 Alternative Concept and Complexity Analysis

> *If objects were created with a default constructor followed by setters, or
> through static factory methods, what would the solution be?*

**Evidence:** `Task04/ObjectCreationComparison.java`, `Task04/alt_output.txt`

| Approach | When is it checked | Can an invalid object exist? |
|---|---|---|
| A - chained constructors | before the object exists | **no** - construction fails instead |
| B - default + setters | per setter, then `seal()` | **yes** - until `seal()` is called |
| C - static factory | inside the factory | no, if the constructor stays `private` |

The window design B opens is demonstrated, not asserted: `new TicketB();
setVehicleNo(...)` produces object #1001 with `usable = false`, `seal()` then
throws `ticket is incomplete` - but the half-built object has **already been
handed a ticket number**, so the counter advanced for a ticket that was never
issued.

Measured over n = 2,000,000 creations, all three are **O(n)** in time and space
and come out within a nanosecond or two of each other, with the ordering varying
between runs. The honest reading is that **creation strategy does not affect
running time at this scale** - every setter is small enough for the JIT to
inline, after which the three loops compile to almost the same machine code.
Space is not identical: `TicketB` carries an extra `sealed` boolean recording
whether it finished being built, a question A and C answer at compile time.

**Decision: A is retained** - on the invariant, not on speed. A `ParkingTicket`
that exists must name a real vehicle in a real slot at a real time, because the
fee is computed from exactly those fields. Only A and C make that true at every
instant, and only A permits `final` fields, which is what actually prevents a
ticket being edited after issue. C would win the moment creation needed a *name*
a constructor cannot carry (`walkIn` versus `atGate`).

# TASK 5 - `static` Members and the Object Life Cycle  *(3 marks, K4)*

**Evidence:** `Task05/StaticMembersDemo.java`, `Task05/actual_output.txt`

## 5.1 What belongs to the class, and what does not

| Member | Scope | Why |
|---|---|---|
| `lastTicketNo` | `static` | one sequence for the whole facility |
| `liveCount` | `static` | occupancy is a property of the facility |
| `totalEverIssued` | `static` | a lifetime total cannot live in one ticket |
| `RATE_BY_TYPE` | `static final` | identical for every ticket; loaded once |
| `ticketNo`, `vehicleNo`, `entryMinute`, `closed` | instance | each ticket's own |

**Why an instance variable would be wrong for the counter.** If `lastTicketNo`
were an instance field, every ticket would start its own count from 1000 and
*all* tickets would be #1001 - breaking "a ticket number is never reused" on the
second vehicle. `CounterScopeComparison` makes that failure happen on screen.

## 5.2 Where a `static` block and `static` methods are appropriate

The rate table is loaded in a **`static` block**, which runs once when the class
is first loaded - before any object exists. The captured output shows
`Ticket.nextTicketNo()` returning 1001 and `Ticket.rateFor(1)` returning 30 with
**no `Ticket` object created yet**. A constructor would rebuild the same table
for every vehicle entering the campus.

`static` methods - `ticketsIssued()`, `vehiclesInside()`, `nextTicketNo()` -
answer questions about the **class**, not about a ticket, so there is no sensible
receiver to call them on.

## 5.3 The object life cycle and garbage collection - observed

A `ParkingTicket` is created at entry, closed at exit, and then has no further
purpose. It becomes eligible for collection when the **last reference**
disappears - which is when the facility removes it from the active list, **not**
when `close()` is called. A `WeakReference` watches the object through three
stages:

| Stage | State | Weak reference resolves |
|---|---|---|
| 1 | inside; held by `activeTickets` and a local variable | **true** |
| 2 | `close()` called; still in the list | **true** |
| 3 | removed from the list, variable set to `null` | **false** - reclaimed |

The ticket *number* is not reused, because it lives in the `static` counter,
which survives the object: the next ticket would be #1005.

## 5.4 Passing and returning objects

`issue()` **returns** a new `Ticket`; the caller never supplies one to fill in,
so a ticket cannot exist half-built. `close()` is called **on** the ticket and
returns a `long` fee rather than an object, so the money leaves as a value and
cannot be altered later through a shared reference.

## 5.5 Alternative Concept and Complexity Analysis

> *If the ticket counter were an instance variable of `ParkingFacility`, what
> happens when the university runs two facilities (north and south gates)?*

**Evidence:** `Task05/CounterScopeComparison.java`, `Task05/alt_output.txt`

Four tickets issued at each of two gates, then merged by the accounts office:

| Design | Distinct numbers | Collisions | Verdict |
|---|---|---|---|
| A - `static` counter | 8 of 8 | 0 | **CORRECT** |
| B - instance counter | 4 of 8 | **4** | **BROKEN** |
| C - instance counter **+ facility code** (`N-1001`, `S-1001`) | 8 of 8 | 0 | **CORRECT** |

Under B every gate restarts at 1001, so ticket #1001 exists twice. The exit
barrier's lookup by ticket number becomes ambiguous and the merged day register
cannot tell which Rs 90 belongs to which vehicle.

**Proposed solution per case:**

| Case | Solution |
|---|---|
| one facility | keep the `static` counter (A) |
| two or more facilities | per-facility counter **+ facility code** (C) |

C is the better long-term answer because it keeps numbers unique *without*
coupling the gates to one shared variable, and the code in the number tells the
accounts office where the ticket came from.

**Space for k facilities and n tickets:**

| Design | Counter space | Per ticket | Total |
|---|---|---|---|
| A | 4 B, **O(1)** | 4 B `int` | 4 + 4n |
| B | 4k B, **O(k)** | 4 B `int` | 4k + 4n |
| C | 4k B, **O(k)** | reference + `String` | 4k + ≈40n |

The counter itself is negligible either way. C's real cost is on the **tickets**:
a `String` identifier such as `"N-1001"` costs ≈40 B against 4 B for an `int` -
about 3.5 MB at n = 100,000. That is the price of global uniqueness, and a
duplicated ticket number is a correctness failure while 3.5 MB is not a
constraint.

**Decision:** `static` in this submission, because the requirement describes one
facility, and because "the next ticket number" is a fact about the ticketing
**sequence**, not about any one ticket or facility object.

# TASK 6 - Design the Inheritance Hierarchy  *(4 marks, K4)*

**Evidence:** `Task06/InheritanceDemo.java`, `Task06/actual_output.txt`,
`docs/original-design.png`

## 6.1 The hierarchy and the kind of inheritance used

```
Vehicle  (abstract)
   |
   +-- TwoWheeler                 <- single
   |
   +-- Car                        <- single
         |
         +-- ElectricCar          <- MULTILEVEL (three levels)

CampusUser  (abstract)
   +-- Student   +-- Staff   +-- Visitor      <- HIERARCHICAL
```

`Vehicle` has two direct subclasses, which makes the vehicle side
**hierarchical**; `ElectricCar` extends `Car` rather than `Vehicle`, which makes
that branch **multilevel**. Java has no multiple class inheritance, so a
capability such as `Chargeable` is an **interface**, not a second superclass.

The full UML class diagram is `docs/original-design.png`
(source: `docs/original-design.mmd`).

## 6.2 What is inherited and what each subclass adds

| Class | Inherits | Adds | Overrides |
|---|---|---|---|
| `Vehicle` | - | `regNo`, `wheels` | - |
| `TwoWheeler` | `regNo`, `wheels`, `describe()` | - | `ratePerHour()` |
| `Car` | `regNo`, `wheels` | `seats` | `ratePerHour()`, `describe()` |
| `ElectricCar` | `regNo`, `wheels`, `seats`, **the car rate** | `batteryKWh` | `describe()` |

`ElectricCar` deliberately does **not** override `ratePerHour()`: an EV parks at
the car tariff and the charging charge is separate. Inheriting the rate is the
design statement that *an EV is-a car for billing purposes*.

## 6.3 `super` used three ways

| Use | Code | Effect |
|---|---|---|
| constructor | `super(regNo, 4)` in `Car` | passes work upward; must be the first statement |
| method | `super.describe()` in `Car` | **extends** rather than replaces the inherited description |
| field | `super.wheels` in `ElectricCar` | reads the inherited field |

Result: `4-wheeler TN03EF3333, 5 seats, electric 40 kWh (wheels field read through super: 4)`

## 6.4 Constructor execution order - traced

Source: `new ElectricCar("TN03EF3333", 40)`

| Step | Event |
|---|---|
| 1 | `ElectricCar(String,int)` entered; `super(regNo, 5)` is its first statement |
| 2 | `Car(String,int)` entered; `super(regNo, 4)` is its first statement |
| **3** | **`Vehicle(String,int)` body runs** - `regNo=TN03EF3333, wheels=4` |
| **4** | **`Car(String,int)` body runs** - `seats=5` |
| **5** | **`ElectricCar(String,int)` body runs** - `battery=40 kWh` |

Lines 3-5 are printed by the constructors themselves, in the order they ran.
**The most general constructor finishes first.** Each subclass constructor
suspends at its `super(...)` call, lets the parent complete, and only then runs
its own body - so a subclass can never read a field the superclass has not yet
initialised. If a constructor omits `super(...)`, the compiler inserts an
implicit no-argument `super()` as its first statement.

Formally: `Vehicle(...) → Car(...) → ElectricCar(...)`.

## 6.5 Alternative Concept and Complexity Analysis

> *If composition were used instead - a single `Vehicle` class that has-a
> `VehicleType` object holding the rate - what would the solution be?*

**Evidence:** `Task06/CompositionComparison.java`, `Task06/alt_output.txt`

| | A - inheritance | B - composition |
|---|---|---|
| the rate is | **behaviour** (an overridden method) | **data** (a field of a shared object) |
| 3 types means | 3 classes | 3 `VehicleType` *instances*, 0 new classes |
| adding a type | 1 new file, **recompile** | `new VehicleType(...)`, **no recompile** |
| fee cost | ≈5.9 ns, virtual call | ≈4.7 ns, one field dereference |
| complexity in k | O(1) | O(1) |
| space per vehicle | ≈16 B | ≈24 B (extra type reference) |

Both produce identical fees on every case tested. **B wins decisively on
extensibility**, and the program proves it by adding a `DELIVERY_VAN` tariff
*at run time* - `new VehicleType("DELIVERY_VAN", 60, 400)` - and billing a van
Rs 180 for 130 minutes with **no class compiled for it**. Design A cannot do
that: a subclass is a compile-time artefact, so a new tariff always means a new
build and a redeploy.

Neither cost depends on the *number* of vehicle types, which is worth stating:
adding a tenth type slows neither design, unlike the `switch` alternative in
Task 7, which grows to O(k).

**Decision: inheritance is retained for this assignment, and the reason is
stated honestly.** The task list requires overriding (Task 7), dynamic dispatch
(Task 8) and an abstract class (Task 9) to be demonstrated, and the composition
design has none of them - its subclass count is zero.

On the engineering merits the two are closer than they look, and composition is
better on the axis the Day-4 challenge actually tests. Vehicle types differ only
in a **rate**, which is data, and inheritance is the wrong tool for varying
data. Inheritance earns its place only where subclasses differ in **behaviour** -
which is exactly what happens in Task 12, where a delivery van's rate depends on
the time of day. The Task 12 redesign therefore **keeps the hierarchy for
identity and moves the tariff into a composed `PricingRule`** - the hybrid that
each of these two designs is half of.

# TASK 7 - Override and Specialise Behaviour  *(4 marks, K4)*

**Evidence:** `Task07/OverrideDemo.java`, `Task07/actual_output.txt`,
`Task07/compile_errors/compiler_errors.txt`

## 7.1 Which methods are overridden, and why

| Method | Overridden in | Why the subclass version is needed |
|---|---|---|
| `ratePerHour()` | every subclass | the tariff genuinely differs per type |
| `toString()` | `Vehicle`, `ElectricCar` | a ticket must print readably |
| `equals()` | `Vehicle` | identity is the **plate**, not the heap address |
| `hashCode()` | `Vehicle` | must stay consistent with `equals()` |
| `calculateFee()` | **nobody - it is `final`** | the billing rule must not vary |

## 7.2 `@Override` and the rules of overriding

* **signature** - name and parameter list must match exactly. `double
  ratePerHour(int)` would be an *overload*, and the abstract method would stay
  unimplemented.
* **return type** - identical, or a subtype (covariant return).
* **access** - may widen (`protected → public`), never narrow.
* **exceptions** - no new or broader checked exception.
* **`static`/`final`** - a `static` method is *hidden*, not overridden; a `final`
  method cannot be overridden at all.

`@Override` changes no behaviour - it asks the **compiler** to verify that a
supertype method really is being replaced. The repository contains the real
compiler output proving both rules:

```
BrokenBike.java:7: error: method does not override or implement a method from a supertype
    @Override protected double ratePerHour(int unused) { return 5; }

SneakyCar.java:6: error: calculateFee(int) in SneakyCar cannot override calculateFee(int) in Vehicle
    @Override public long calculateFee(int m) { return 0; }
  overridden method is final
```

Without `@Override` the first example would compile cleanly as a brand-new
method, and every `BrokenBike` would be billed at the inherited Rs 10/hour while
the author believed the rate was Rs 5.

## 7.3 Where `final` is appropriate

| Declaration | Kind | Reason |
|---|---|---|
| `private final String regNo` | variable | identity must not change after `equals()` depends on it |
| `static final MINUTES_PER_HOUR` | constant | a unit conversion is not configurable |
| `public final calculateFee()` | **method** | the billing **rule** is fixed; only the rate varies |
| `final class ElectricCar` | class | closes the branch; no hidden re-specialisation |

The `final` on `calculateFee()` is the important one. It is what makes the design
safe: a subclass may change **what it costs per hour**, but can never change the
rule that a part-hour is charged as a whole hour - so no future vehicle type can
quietly under-bill the campus. The second compiler error above is that guarantee
being enforced.

## 7.4 `toString()`, `equals()` and `hashCode()`

```java
@Override public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Vehicle)) return false;       // Vehicle, NOT getClass()
    return regNo.equals(((Vehicle) o).regNo);
}
@Override public int hashCode() { return regNo.hashCode(); }
```

| Comparison | Result |
|---|---|
| `carA == carB` (reference identity) | `false` |
| `carA.equals(carB)` (same plate, same class) | **`true`** |
| `carA.equals(evSame)` (same plate, **subclass**) | **`true`** |
| `carA.equals(other)` (different plate) | `false` |
| `carA.hashCode() == carB.hashCode()` | **`true`** |

**Why `instanceof Vehicle` and not `getClass()`.** One physical car has one
number plate. If the same plate were registered once as a `Car` and once as an
`ElectricCar` - a plausible data-entry difference - they are still the same car
and the facility must refuse the duplicate. A `getClass()` comparison would call
them different and let one vehicle occupy two slots. The cost is that `equals()`
is no longer symmetric with a subclass that adds its own equality fields, which
is precisely why `ElectricCar` is declared **`final`**.

**The consequence, demonstrated:**

```
add(carA)   -> true    (new vehicle admitted)
add(carB)   -> false   (same plate: REFUSED as a duplicate)
add(evSame) -> false   (same plate: REFUSED as a duplicate)
vehicles recorded inside = 2  (expected 2)

entryMinute.get(carB)   -> 540   (found with a DIFFERENT object, same plate)
entryMinute.get(evSame) -> 540   (found across the subclass too)
```

This is the whole point of overriding `hashCode()` alongside `equals()`: the exit
barrier can look a vehicle up from a freshly scanned plate without holding the
original object. With `Object`'s identity hash, `get(carB)` would return `null`
and **no vehicle could ever leave**.

## 7.5 Alternative Concept and Complexity Analysis

> *If a single `calculateFee()` with a `switch` on a type field were used instead
> of overriding, what would the solution be?*

**Evidence:** `Task07/SwitchFeeComparison.java`, `Task07/alt_output.txt`

Measured with k = 12 vehicle types, 10,000,000 calls each:

| Design | Per fee (ns) | Complexity in k |
|---|---|---|
| A - overriding (dispatch) | 6.38 | **O(1)** |
| B - `switch` on `int` type | 6.41 | **O(1) - jump table** |
| B' - `if-else` chain, mixed types | 5.48 | O(k), average k/2 |
| B' - `if-else`, **first** type only | **3.85** | 1 test |
| B' - `if-else`, **last** type only | **6.25** | 12 tests |

**An honest correction to the textbook claim.** A dense `int` `switch` compiles
to `tableswitch` - a jump table - so it is **O(1) in k, not O(k)**. The O(k)
claim holds only for a *sparse* switch (`lookupswitch`, O(log k)) or for an
`if-else` chain. The last two rows measure exactly that: the same chain costs
measurably more for the last type than for the first.

| Design | New code | Existing code | If a site is missed |
|---|---|---|---|
| A - overriding | 1 new class | **0 changed** | **compile error** |
| B - `switch` | 0 new classes | 1 per switch | **silent wrong answer** |

The real cost of B is not the one switch shown. A working system switches on
type in several places - the rate, the daily cap, the slot-size check, the
display name, the receipt line. Each is a separate switch, and the compiler
cannot tell you that you updated four of the five.

**Decision: overriding is retained, but not on grounds of speed** - the
difference between dispatch and a dense `switch` is within noise. It is retained
because it moves the question *"did you handle every type?"* from run time to
compile time, and because it keeps each type's rules in one place.

# TASK 8 - Apply Polymorphism  *(4 marks, K4)*

**Evidence:** `Task08/FeeDemo.java` (Complete the Code),
`Task08/PolymorphismDemo.java`, `Task08/EQUALS_BEHAVIOUR.md`

## 8.1 Compile-time polymorphism: overloaded `calculateFee`

Three overloads exist, and the **compiler** chooses between them from the
**static** types of the arguments:

| Call | Chosen overload | Why |
|---|---|---|
| `calculateFee(130)` | `calculateFee(int)` | exact match |
| `calculateFee(130L)` | `calculateFee(long)` | exact match; narrowing is never implicit |
| `calculateFee(LocalTime, LocalTime)` | the 2-argument form | only one is applicable |
| `calculateFee(shortValue)` | `calculateFee(int)` | `short` **widens** to `int`; the narrowest applicable widening wins |

Selection runs in three phases - exact match, then widening, then
boxing/varargs - and if two candidates are equally specific it is an
**ambiguity error**, not a runtime choice. The object's real class plays no part
in this decision.

## 8.2 Upcasting: one array, three types

```java
Vehicle[] parked = { new TwoWheeler(..), new Car(..), new ElectricCar(..) };
```

| Index | Declared type | Actual class | Assignment needed |
|---|---|---|---|
| 0 | `Vehicle` | `TwoWheeler` | none - the upcast is implicit |
| 1 | `Vehicle` | `Car` | none |
| 2 | `Vehicle` | `ElectricCar` | none |

The upcast is implicit and always safe, because every element really *is-a*
`Vehicle`. The array's element type is the **contract**, not the implementation.

## 8.3 Runtime polymorphism: dynamic method dispatch, traced

One line of source - `long fee = v.calculateFee(130);` - executed three times:

| Element | Declared type | Actual object type | Body that ran | Fee |
|---|---|---|---|---|
| `TwoWheeler TN01A1` | `Vehicle` | `TwoWheeler` | `TwoWheeler.ratePerHour() → 10` | Rs 30 |
| `Car TN02B2` | `Vehicle` | `Car` | `Car.ratePerHour() → 30` | Rs 90 |
| `ElectricCar TN03C3` | `Vehicle` | `ElectricCar` | **`Car.ratePerHour() → 30`** (inherited) | Rs 210 (incl. charging) |

**The mechanism.** `calculateFee()` is resolved at compile time, but the
`ratePerHour()` call inside it compiles to `invokevirtual`. At run time the JVM
reads the object's header, finds its class, looks `ratePerHour()` up in that
class's method table and jumps there. **The declared type decides what may be
called; the actual type decides which body runs.**

## 8.4 Why this avoids a long `if-else` chain

The chain produces the same answers today but is the worse design:

* **Order matters.** `ElectricCar` must be tested *before* `Car`, because an
  `ElectricCar` is-a `Car` and the `Car` branch would otherwise swallow it.
  Reordering two lines silently changes the bill.
* It lives **outside** the classes, so adding a type means editing a method that
  already works and was already tested.
* The final `else` is reachable, so "unknown vehicle type" is a runtime error the
  compiler cannot warn about. With dispatch that branch does not exist.

| | Output |
|---|---|

| **Actual** | identical - `diff` reports no difference |

## 8.6 Why the last line prints `true` - and is that correct?

```java
System.out.println(new Car("TN02B2").equals(new ElectricCar("TN02B2")));   // true
```

**Why.** `equals()` is overridden once, in `Vehicle`, and tests `instanceof
Vehicle` rather than `getClass()`. An `ElectricCar` *is* a `Vehicle`, both carry
the plate `"TN02B2"`, and no subclass adds a field to the comparison - so two
distinct objects of two different classes compare equal, because the design has
declared that **a vehicle's identity is its number plate**.

**Is it correct for this system? Yes - and it is the behaviour the system
needs.** A plate identifies one real vehicle; it cannot be in two slots at once.
The duplicate-entry check is `contains(scannedVehicle)`, and the exit barrier
constructs a **fresh** object from a scanned plate to look the stay up. Without
this definition of equality, `tickets.get(scanned)` returns `null` and no vehicle
can leave. Crossing the class boundary is correct too: a plate recorded once as
a `Car` and once as an `ElectricCar` is still the same car.

**The cost, and how it is contained.** `instanceof` breaks the *symmetry* clause
of the `equals()` contract if a subclass ever adds equality fields. This is
contained deliberately: no subclass overrides `equals()`, and `ElectricCar` is
declared `final`, so the branch is closed.

The full discussion, including where this choice would be *wrong*, is in
`Task08/EQUALS_BEHAVIOUR.md`.

> *If the same behaviour were written using `instanceof` checks and casting,
> what would the solution be?*

**Evidence:** `Task08/InstanceofComparison.java`, `Task08/alt_output.txt`

Measured with k = 12 types, 10,000,000 calls:

| Call pattern | Per call (ns) | Tests performed |
|---|---|---|
| A - dispatch, all k types mixed | 6.33 | 0 - one indirect jump |
| B - `instanceof`, all k types mixed | ≈6 | 1...k, average 6 |
| B - `instanceof`, **first** type only | **4.10** | 1 |
| B - `instanceof`, **last** type only | **8.92** | 12 |
| A - dispatch, last type only | 6.33 | 0 |

Cost of being last in the chain: **2.2×**. Dispatch is **position-independent**.

| Design | Best | Worst |
|---|---|---|

# TASK 9 - Introduce Abstraction  *(4 marks, K4)*

**Evidence:** `Task09/AbstractionDemo.java`,
`Task09/compile_errors/compiler_errors.txt`

## 9.1 Which class is abstract, which methods are abstract

| Type | Kind | Why this kind |
|---|---|---|
| `Vehicle` | **abstract class** | holds state (`regNo`, `wheels`) and a validating constructor |
| `ratePerHour()` | **abstract method** | every type has one; none can be inherited |
| `dailyCap()` | concrete method | a default exists; may be specialised |
| `calculateFee()` | **`final` method** | the billing rule must not vary |
| `Chargeable` | **interface** | an optional capability, not a kind of thing |
| `Payable` | **interface** | cuts across vehicles **and** users |
| `Identifiable` | **interface** | anything loggable; needs no shared state |

## 9.2 Why an abstract class in one place and an interface in another

`Vehicle` **must** be an abstract class, because it needs three things an
interface cannot provide:

1. **instance state** - `regNo` and `wheels` are fields, not constants;
2. **a constructor** that validates `regNo` before any object exists;
3. **a partly-written algorithm** - `calculateFee()` calls down into an abstract
   step, the template-method pattern.

`Chargeable` **must** be an interface, because charging is a **capability**, not
a kind of vehicle: it has no state of its own, it cuts **across** the hierarchy
(an electric car and a future e-bike are both chargeable but are not relatives),
and Java allows only one superclass - making it a class would permanently consume
`ElectricCar`'s single inheritance slot.

The test applied throughout: **if the answer to "what *is* it?" - abstract class.
If the answer to "what can it *do*?" - interface.**

Both halves are proved by real compiler errors in the repository:

```
InstantiateAbstract.java:7: error: Vehicle is abstract; cannot be instantiated
BadInterface.java:6: error: = expected          // an interface field is implicitly static final
BadInterface.java:7: error: <identifier> expected // an interface cannot declare a constructor
```

The first proves nobody can park "a vehicle" with no type and therefore no rate.
The second proves an interface could not have done `Vehicle`'s job.

## 9.3 Multiple behaviours through interfaces

`class ElectricCar extends Car implements Chargeable` - one superclass, three
usable types:

| Question | Answer |
|---|---|
| is-a `Vehicle` (via `Car`) | `true` |
| is-a `Car` | `true` |
| can-do `Chargeable` | `true` |
| can-do `Identifiable` (inherited) | `true` |

The same object can be handed to a method wanting a `Vehicle`, one wanting a
`Chargeable`, and a logger wanting an `Identifiable` - each seeing only the part
that concerns it.

## 9.4 Where a `default` and a `static` interface method are useful

**`default`** - `needsChargingSlot()` returns `true` for almost every chargeable
vehicle, so writing it in every implementer would be repetition; yet a
`HybridCar` genuinely differs and **overrides it to `false`**. A default gives
the common answer for free *and* lets the exception override it. It is also how
a capability can gain a method later without breaking existing implementers.

**`static`** - `Chargeable.estimateUnits(40, 80) → 32.0 kWh` is a helper about
charging *in general*; it needs no vehicle at all. Before Java 8 it would have
gone into a separate `ChargingUtils` class, far from the contract it serves. As
a `static` interface method it sits with the capability and, because it cannot be
inherited or overridden, its answer is the same everywhere.

## 9.5 The abstraction in use

```
CLASS          | REG NO       | PARK 130m  | CHARGEABLE  | CHARGE 10kWh | TOTAL
TwoWheeler     | TN01AB1111   | Rs 30      | no          | Rs 0         | Rs 30
Car            | TN02CD2222   | Rs 90      | no          | Rs 0         | Rs 90
ElectricCar    | TN03EF3333   | Rs 90      | yes         | Rs 120       | Rs 210
HybridCar      | TN08PQ8888   | Rs 90      | yes         | Rs 120       | Rs 210
```

The loop body **names no concrete vehicle class**. It knows only that every
element can be billed (`Vehicle`) and that *some* can be charged (`Chargeable`).

`PassHolder` does not implement `Payable`, so `amountDue()` cannot even be
*called* on one - the free-parking rule is enforced by the **type system** rather
than by an `if` somebody could forget to write.

## 9.6 Alternative Concept and Complexity Analysis

> *If `Vehicle` were an interface with default methods, and `Chargeable` an
> abstract class, what would the solution be?*

**Evidence:** `Task09/InvertedAbstractionComparison.java`, `Task09/alt_output.txt`

The swap compiles and runs, and produces identical fees - that is worth stating
before the criticism. What is **lost**:

| Capability | Original | Swapped |
|---|---|---|
| instance state | `regNo` in `Vehicle` | **LOST** - repeated in every class |
| constructor | validates `regNo` once | **LOST** - repeated in every class |
| `final` method | `calculateFee` is `final` | **LOST** - a default is overridable |
| `protected` member | available to subclasses | **LOST** - interface members are public |
| multiple capability | 1 class + N interfaces | **LOST** - 1 abstract class only |

**The serious loss.** A `default` method cannot be `final`, so this class is
**legal** in the swapped design:

```java
@Override public long calculateFee(int m) { return 0; }
```

`BFreeloader` parked 130 minutes → **Rs 0** where it should be Rs 90. In the
original design the same class does not compile. *The swap turns a compile-time
guarantee about revenue into an honour system.*

**Multiple inheritance of capability** is lost too: `Chargeable` as an abstract
class consumes the single inheritance slot, so `BElectricCar` can no longer
extend `Car` - note that its `ratePerHour()` returns 30 as a **copied literal**
rather than inheriting the car tariff. Change the car rate and the EV silently
keeps the old one.

| | Per call (ns) | Bytecode | Space per object |
|---|---|---|---|
| A - abstract class | 4.04 | `invokevirtual` | 16 B |
| B - interface + default | 6.19 | `invokeinterface` | 16 B |

Per-object space is **unchanged** - the field has to exist either way; design B
merely moves its *declaration* into each implementer, which costs source lines,
not heap. The time difference is of the order of a nanosecond.

**Decision: the original is retained**, argued on design rather than cost. The
swap inverts the two questions each construct answers: an abstract class answers
*"what is this?"* and a vehicle **is** something; an interface answers *"what can
it do?"* and charging is something a vehicle **may** do. Swapping them makes
identity optional and capability exclusive - exactly backwards - and the concrete
price is `BFreeloader`.

## 10.1 Package structure

## 10.2 Access modifier for each member, and why

| Member | Modifier | Reason |
|---|---|---|
| `Vehicle.regNo` | `private` | identity; no code anywhere may change it |
| `Vehicle(String,int)` | `protected` | only subclasses build vehicles |
| `Vehicle.ratePerHour()` | `protected` | a raw rate is a model-internal detail |

## 10.3 How getters and setters validate

Every attempt below was made by the application package and **rejected**:

| Attempt | Outcome |
|---|---|
| `new Car("")` | `IllegalArgumentException` - registration number is mandatory |
| `new ElectricCar("TN9", 0)` | battery capacity must be positive |
| `t1.setExitMinute(400)` (before entry) | exit (400) cannot precede entry (540) |
| `t1.setExitMinute(2000)` | exit minute must be 0..1439 |
| `ev.chargingFee(-5)` | units drawn cannot be negative |
| `bike.calculateFee(-30)` | duration cannot be negative |
| `f.admit(bike, 600)` (already inside) | `IllegalStateException` |
| `new Facility(new int[]{0})` | every floor needs at least one slot |

The constructor also **normalises**: `" tn01ab1111 "` becomes `"TN01AB1111"`, so
the plate used as a lookup key is canonical.

Each guard lives in exactly **one** place - the setter or constructor of the
class that owns the field - so no caller can skip it and no caller has to
remember it. *That* is the practical payoff of private fields: the check cannot
be bypassed because the field cannot be reached.

## 10.4 What the application package cannot do

Four real compiler errors, captured in `compile_errors/compiler_errors.txt`:

```
error: free() is not public in Slot; cannot be accessed from outside package
error: Slot(int,int) is not public in Slot; cannot be accessed from outside package
error: ratePerHour() has protected access in Car
error: SlotGrid is not public in parking.service; cannot be accessed from outside package
error: calculateFee(int) in FreeParkingCar cannot override calculateFee(int) in Vehicle
         overridden method is final
```

**Those errors *are* the encapsulation.** Each is a business rule enforced by the
compiler: a slot's occupancy can change only through the facility; the storage
layout can be replaced without breaking any caller; and no future vehicle type
can make parking free.

## 10.5 Wrapper classes, autoboxing, and the risk

| Site | Type | Why not a primitive |
|---|---|---|
| `ParkingTicket.exitMinute` | **`Integer`** | `null` means "still inside"; **0 is midnight**, a real time |
| `Map<String,Integer>` | `Integer` | a generic type cannot hold `int` |
| slot, floor, duration | `int` | always present - primitive is correct |
| fee | `long` | always present - primitive is correct |

**The `==` trap:**

| Comparison | Result | Why |
|---|---|---|
| `Integer 90 == Integer 90` | **`true`** | both from the -128...127 cache |
| `Integer 900 == Integer 900` | **`false`** | two distinct objects on the heap |
| `Integer 900 .equals(Integer 900)` | `true` | compares the **value** - always right |
| `Integer 900 == 900` (mixed) | `true` | the `Integer` is **unboxed** first |

This is the worst possible failure mode: `==` on `Integer` is correct for every
value from -128 to 127 and wrong above it. **A fee comparison tested with Rs 90
would pass every test and fail in production the first time a vehicle was billed
Rs 200** - which the program demonstrates on an actual fee map.

Two further hazards, both demonstrated:

* **`NullPointerException` on unboxing** - `int d = exitMinute - 540;` throws when
  `exitMinute` is `null`. This is why `durationMinutes()` tests
  `if (exitMinute == null) return -1;` **before** any arithmetic: the subtraction
  looks harmless but hides an unboxing call.
* **`remove(int)` versus `remove(Object)`** - `list.remove(1)` removes **index 1**;
  `list.remove(Integer.valueOf(1002))` removes the **value**. Ticket numbers are
  therefore `int`, and the active register is a `List<ParkingTicket>`.

**Measured boxing cost** over 20,000,000 additions: a `long` accumulator creates
**0** objects; a `Long` accumulator creates **one object per addition**, because
wrappers are immutable. That is the third reason money fields are primitive
`long`.

**The rule applied throughout: a wrapper only where absence is meaningful or a
generic type demands it.**

## 10.6 Alternative Concept and Complexity Analysis

> *If the fields were public and validation were done by the calling code, what
> would the solution be and what could go wrong?*

**Evidence:** `Task10/PublicFieldsComparison.java`, `Task10/alt_output.txt`

The same four mistakes, in both designs:

| Mistake | A - private + setter | B - public fields |
|---|---|---|
| exit (400) before entry (540) | rejected | **ACCEPTED, duration -140** |
| exit minute 5000 | rejected | **ACCEPTED, duration 4460** |
| blank plate | rejected | **ACCEPTED, plate `"  "`** |
| `" tn04gh4444 "` normalised? | yes → `TN04GH4444` | **no** |

Design B accepted all four. None threw, none logged anything. The negative
duration is the dangerous one: a fee computed from it is Rs 0 or negative, so
*the facility pays the driver to park*. The untidy plate is worse than it looks -
`" tn04gh4444 "` and `"TN04GH4444"` are different `HashMap` keys, so the vehicle
that entered **cannot be found at the exit barrier**.

Note that the validation function `validateB()` **exists and is correct**. The
failure is not that the check is missing - it is that *nothing forces a caller to
run it*.

**Where the check must be repeated:**

| Call site that writes a field | A | B |
|---|---|---|
| `Facility.admit()`, `release()`, the gate console, the batch importer, the re-issue path, the test harness | 0 checks each | 4 checks each |
| **Total for 6 call sites, 4 rules** | **4** (once, in the class) | **24** |

With s call sites and r rules, A is **O(r)**; B is **O(r × s)**, and every copy is
a place a future rule change can be forgotten.

**Measured cost of validation:**

| Update path | Per update (ns) | Checks |
|---|---|---|
| A - setter with validation | 3.76 | 3 |
| B - bare public field write | 2.05 | **0 - unsafe** |
| B - field write + `validateB()` | 4.96 | 4 |

The difference is real but small, and the same order as the explicit
`validateB()` row - confirming the cost is the **checks**, not the method call.
Against the real workload (≈5,000 updates a day for a 320-slot facility turning
over four times), that is a few microseconds per day. **There is no performance
case for removing it.**

**Decision: A is retained.** The designs differ in *where a mistake surfaces*. In
A an invalid update throws at the point of the mistake with a message naming the
rule; in B it succeeds, and the consequence appears later as a wrong fee or a
vehicle that cannot leave. Public fields also freeze the representation: once
callers write `t.exitMinute` directly, it can never become an `Integer`, a
`LocalTime` or a computed value. **The private field plus setter is what makes
the Task 12 redesign possible at all.**

## 11.5 One limitation of the design - stated plainly

**The tariff is welded to the vehicle type.** `ratePerHour()` is an overridden
method, so the design can express *"a car costs more than a bike"* but cannot
express *"this vehicle costs more between 9 and 5"*, because the rate has no
access to the clock. Any pricing rule that depends on something other than the
vehicle's class has nowhere to live.

This is not a hypothetical weakness. It is exactly the requirement the Day-4
challenge introduces, and Task 12 is the response.

A second, smaller limitation: the active-ticket store is a `List`, so exit lookup
is O(n) - quantified immediately below.

## 11.6 Alternative Concept and Complexity Analysis

> *If active tickets were stored in an `ArrayList` or a `HashMap` keyed by
> registration number, what would exit processing become?*

**Evidence:** `Task11/TicketStoreComparison.java`, `Task11/alt_output.txt`

Workload: fill the store with n tickets, then process **every** vehicle's exit in
a shuffled order.

| n | A - array (ms) | B - ArrayList (ms) | C - HashMap (ms) | C faster by |
|---|---|---|---|---|
| 320 | 0.10 | 0.62 | **0.02** | 5× |
| 1,000 | 0.89 | 5.91 | **0.07** | 13× |
| 5,000 | 22.68 | 105.33 | **0.83** | 27× |
| 20,000 | 849.85 | 503.62 | **2.51** | 339× |
| 50,000 | 5,322.99 | 3,964.87 | **2.32** | **2,295×** |

Per-operation cost, microseconds - **this is the shape that matters**:

| n | A - array | B - list | C - map |
|---|---|---|---|
| 320 | 0.3024 | 1.9220 | **0.0666** |
| 5,000 | 4.5352 | 21.0669 | **0.1656** |
| 50,000 | **106.4599** | 79.2973 | **0.0464** |

A and B grow in proportion to n *per operation*, so the **total** grows as n².
C's per-operation column stays flat while n grows by a factor of 150.

| Operation | A array | B ArrayList | C HashMap |
|---|---|---|---|
| find on exit | O(n) | O(n) | **O(1)** expected |
| remove after find | O(1) swap | **O(n) shift** | O(1) |
| duplicate check at entry | O(n) | O(n) | **O(1) - free** |
| **a full day, n exits** | **O(n²)** | **O(n²)** | **O(n)** |
| list all inside | O(n) | O(n) | O(n), but **loses order** |

| Structure | Overhead per vehicle | n = 320 |
|---|---|---|
| A - array | 4 B reference | 1,280 B |
| B - ArrayList | 4 B + up to 50 % spare | ≈1,920 B |
| C - HashMap | 4 B + `Node` ≈32 B + table | ≈12 KB |

C costs roughly 10× the per-vehicle overhead - a few kilobytes - while the time
difference is already 5× at n = 320 and grows without limit.

**This is the one place in the whole assignment where the alternative is simply
better rather than a trade-off.**

**Recommendation:** replace the active-ticket `List` with a
**`LinkedHashMap<String, ParkingTicket>`** keyed by registration number.
`LinkedHashMap` rather than `HashMap` because the facility must also **list** the
vehicles inside - for the occupancy report and end-of-day reconciliation - and a
plain `HashMap` returns them in an arbitrary order that changes between runs,
making a report impossible to check by hand. `LinkedHashMap` keeps O(1) lookup
**and** entry order for one extra pair of pointers per entry.

**Why the Task 11 code still uses a `List`:** the change touches only the
**private** field `active` inside `ParkingFacility`. Because that field is
private and every caller goes through `admit()` and `release()`, the
substitution is invisible outside the class. That is the practical proof that
the Task 10 encapsulation was worth having - and Task 12 carries the change out.

# TASK 12 - DAY-4 DESIGN CHALLENGE: Re-evaluate and Adapt the Design  *(8 marks, K5)*

## A. Impact Analysis  *(2 marks)*

### A.1 What has changed from the original problem

| # | Change | Nature |

### A.3 Why a different number of slots on each floor affects the array design

It does not - **and that is the finding.** The Task 2 analysis chose a jagged
`String[f][]` precisely because `slots[f].length` carries each floor's size as
part of the structure. Extending to `{20, 50, 50, 80, 12}` required passing a
longer `int[]` to the constructor and **no code change at all**, which test rows
A1-A3 verify: 5 floors, capacity 212, and each floor reporting its own size.

Had the slots been stored in a flat array with a single stride, the change would
have been **impossible to make correctly**: with sizes 20/50/50/80/12 no one
stride works - `floor × 80` leaves dead cells, `floor × 20` makes floor 1 slot 25
collide with floor 2 slot 5. The flat form would have had to grow a prefix-sum
array, i.e. re-state the floor sizes by hand. **This is the Task 2 analysis being
cashed in.**

|---|---|

## B. Evaluation of the Original Design  *(2 marks)*

### B.1 Can new vehicle types be added only by writing new subclasses?

**Partly - and the exception is decisive.**

| New category | Could the original handle it? |
|---|---|
| e-bike, flat fee | **No.** `calculateFee()` is `final` and computes `hours × rate`. A flat fee is not of that form, so there is no value `ratePerHour()` could return. The only route would be to un-`final` `calculateFee()` - which is exactly the guarantee Task 7 argued hardest to keep. |
| delivery van, 09:00-17:00 | **No.** `ratePerHour()` takes no arguments and so cannot see the clock. The rate is not a property of the van. |

The original design is open to new vehicle types **only when the new type differs
by a constant rate**. Both new categories fall outside that, so the design fails
its own extensibility claim on the first real test.

### B.2 Are the pricing rules spread across many classes or kept in one place?

**Spread - this is the second structural flaw.** In the original, prices lived as
literals inside five separate classes:

| Class | Price literals |
|---|---|
| `TwoWheeler` | `return 10;` and `return 60;` |
| `Car` | `return 30;` |
| `ElectricCar` | (inherits 30) |
| `Chargeable` | `RATE_PER_KWH = 12.0` |
| `Vehicle` | `return 200;` (default cap) |

A tariff revision - an entirely routine event for a car park - means editing five
compiled classes and re-testing all of them. There is no single place to read
"what does the campus charge?", and no way to load prices from configuration.

### B.3 Can the existing tested classes remain unchanged?

**No - and the honest answer is that this is a real cost of the redesign.** Six
existing classes had to change: `Vehicle` plus all five vehicle classes, each in
its constructor. `CampusUser` and `UserCategory` changed for the pass, and
`Slot`, `SlotFactory` and `SlotGrid` changed for sizing.

What **did** remain unchanged is worth listing, because it is what makes this a
modification rather than a rewrite: the plate invariant and `equals`/`hashCode`;
the `final` billing guarantee; the jagged array; the package boundary and every
access modifier; and the entire application-facing API shape.

---

## C. Adaptation or Redesign  *(2 marks)*

**Decision: MODIFY.** Three changes, each isolated.

### C.1 A `PricingRule` abstraction - the tariff becomes an object

```java
public interface PricingRule {
    long fee(int entryMinute, int exitMinute);
    String describe();
    static int duration(int entry, int exit) { ... }       // handles midnight wrap
    static int startedHours(int minutes) { return (minutes + 59) / 60; }
}
```

| Implementation | Expresses |
|---|---|
| `HourlyRate` | the original tariff - a flat rate per started hour |
| `FlatFee` | **new** - e-bikes |
| `TimeOfDayRate` | **new** - a peak window with a multiplier |
| `CappedRule` | a **decorator** applying a daily maximum to *any* other rule |
| `Tariffs` | a utility assembling the five tariffs - **the one place every price is stated** |

`Vehicle` keeps its hierarchy and its `final` fee method, but **has-a**
`PricingRule` instead of overriding a rate:

```java
public final long parkingFee(int entryMinute, int exitMinute) {
    return pricing.fee(entryMinute, exitMinute);
}
```

This is the hybrid the Task 6 analysis predicted: **inheritance for identity,
composition for the tariff.**

`CappedRule` deserves a note. The cap used to be an overridable method, so every
new type had to remember to set one. As a wrapper it is applied once where the
tariff is assembled and composes with any rule - including rules written in the
future. That is what "extend without modifying" means in practice.

### C.2 A `Pass` interface - entitlement becomes an object

```java
public interface Pass {
    boolean coversStay(int dayOfYear, int entryMinute);
    long priceWhenSold();
    Pass NONE = ...;                      // null object: no pass at all
}
```

`MonthlyPass` covers a range of days; **`OneDayPass`** covers exactly one.
`CampusUser.paysFee(day, minute)` now asks the pass rather than consulting a
boolean and an enum rule. The `NONE` null object removes a null check from every
call site.

### C.3 A ragged, typed facility

`VehicleCategory` gains `slotUnits()`; `Slot` gains `units` and
`fits(VehicleCategory)`; `SlotGrid` skips a floor whose slots are too small. The
jagged array itself is untouched.

`ParkingFacility` also adopts the **`LinkedHashMap`** that Task 11's measurements
recommended, so exit lookup and the duplicate check are now O(1) instead of O(n).

### C.4 The new categories, implemented

```java
public final class EBike extends Vehicle implements Chargeable {
    public EBike(String regNo) { super(regNo, VehicleCategory.E_BIKE, Tariffs.eBike()); }
    @Override public double chargingFee(int kWh) { ... }
}

public final class DeliveryVan extends Vehicle {
    public DeliveryVan(String regNo) {
        super(regNo, VehicleCategory.DELIVERY_VAN, Tariffs.deliveryVan());
    }
}
```

Neither contains a rate, a cap or a fee method.

### D.4 Trade-offs

| Gained | Cost |
|---|---|
| tariffs that depend on time, not only on type | one more object per vehicle (a `PricingRule` reference) |
| every price in **one** file (`Tariffs`) | an extra level of indirection when reading the code |
| new categories add **0** modifications | the abstraction cost **6** modified classes up front |
| rules compose (`CappedRule` wraps anything) | a composed rule is harder to read than `return 30;` |
| entitlement carries a date | `ParkingTicket` and the facility API gained a `dayOfYear` parameter |
| O(1) exit lookup | ≈32 B of `Node` overhead per parked vehicle |

**The honest objection** to this redesign is that it adds indirection for a car
park of 212 slots, where none of the performance differences matter at all. The
answer is that **the indirection is not bought for speed - it is bought for the
ability to state a rule the old design could not state at any price.** The
delivery van is not a performance problem; it is an *expressiveness* problem, and
no amount of tuning the original would have solved it.

### D.5 The final decision, following from the analysis

**MODIFY - keep the hierarchy, replace the tariff mechanism.**

1. **Retain is not available.** B.1 shows the original cannot express either new
   category: a flat fee is not of the form `hours × rate`, and `ratePerHour()`
   cannot see a clock. The only "retain" route is to un-`final` `calculateFee()`,
   which `Task09/InvertedAbstractionComparison` measured the cost of -
   `BFreeloader` bills **Rs 0** where Rs 90 is due.
2. **Full redesign is not warranted.** The regression rows C1-C10 show the
   original's *identity* model - the plate invariant, `equals`/`hashCode`, the
   `final` billing guarantee, the jagged array, the package boundary - all
   survive unchanged and still pass. Discarding them would mean re-proving work
   that is already correct.
3. **Modify is what the evidence supports.** The one thing the original got
   structurally wrong was welding a *varying* quantity (price) into an
   *inheritance* relationship. The redesign moves exactly that one thing out -
   and the measured consequence is that two new vehicle categories, a new pass
   type and a seasonal tariff cost **zero modifications** between them.

The deciding sentence is from the Task 6 analysis, written before the challenge
was attempted: *"inheritance earns its place only where the subclasses differ in
behaviour."* Vehicle types differ in a **rate**, which is data; what differs in
**behaviour** is the pricing **rule**. Putting the hierarchy where the identity
is, and the composition where the variation is, is the design the evidence points
to - and 64 passing tests, including a full regression of the original
behaviour, are what back it.
