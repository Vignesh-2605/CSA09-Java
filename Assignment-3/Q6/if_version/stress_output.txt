3.  WHAT THE FAILURE ACTUALLY IS
--------------------------------------------------------------------------------------------------------
  interleaving that breaks the if version, with consumers C1 and C2:
    1. C1 calls take(), finds count == 0, calls wait() and releases the lock
    2. C2 calls take(), finds count == 0, calls wait() and releases the lock
    3. producer calls put(), stores one token, count becomes 1, notifyAll()
    4. C1 re-acquires the lock, and because it used if it does NOT re-test;
       it consumes the token, count becomes 0
    5. C2 re-acquires the lock and also does not re-test.  It reads
       buffer[out] - a slot that holds a STALE token - and decrements
       count to -1

  So a token is counted twice and the invariant 0 <= count <= capacity is
  broken.  The negative count in the table above is that invariant being
  violated, observed rather than argued.

  WHY wait() MUST ALSO BE INSIDE synchronized: wait() releases the
  monitor, so the caller must hold it first.  Calling it without the lock
  throws IllegalMonitorStateException:
    new Object().wait(1) outside synchronized -> IllegalMonitorStateException

  More fundamentally, testing the condition and waiting must be ONE
  atomic step.  If the test were outside the lock, the condition could
  change between the test and the wait, and the thread would sleep
  waiting for a notification that has already been sent - a lost wakeup,
  which hangs the program permanently.

4.  sleep() AND wait() ARE NOT INTERCHANGEABLE
--------------------------------------------------------------------------------------------------------
                       | Thread.sleep(ms)           | Object.wait()              | CONSEQUENCE HERE
--------------------------------------------------------------------------------------------------------
declared on            | Thread (static)            | Object (instance)          | wait belongs to the monitor
releases the lock      | NO                         | YES                        | sleep inside put() would freeze the counter
woken by               | time only                  | notify/notifyAll or time   | wait reacts to the state changing
needs the lock         | no                         | yes                        | IllegalMonitorStateException otherwise
used for               | pacing / simulation        | waiting for a condition    | they solve different problems

  The decisive row is the second.  If the consumer used sleep() while the
  counter was empty, it would hold the lock the whole time, so the
  producer could never enter put() to supply the token the consumer is
  waiting for.  That is not slow - it is a permanent deadlock.
