  QTY is a word, so Long.parseLong throws NumberFormatException

    LOG  twr:    store file store04.csv    failed: NumberFormatException: For input string: "SEVEN"

  VERSION                    | OUTCOME            | STORE FDs STILL OPEN       | REPORT WRITTEN?
  --------------------------------------------------------------------------------------------------------
  manual close()             | threw IOException  | 1 leaked                   | partial (3 of 6 stores)
  try-with-resources         | threw IOException  | 0 leaked                   | partial (3 of 6 stores)

  Counted by reading /proc/self/fd and following each symbolic link,

  Both versions abandon the report.  Only one leaks the handle.

3.  THE LEAK COMPOUNDS  -  THE "TOO MANY OPEN FILES" SYMPTOM
----------------------------------------------------------------------------------------------------------------
  The retail chain's complaint is not one leaked handle, it is the
  process eventually refusing to open anything.  Reproduced by running
  the manual version repeatedly WITHOUT letting the leak be collected,
  under a deliberately low descriptor limit (see ulimit_demo.txt).
  handles opened and retained before failure : 19988
  what stopped it                            : FileNotFoundException: stores/store01.csv (Too many open files)
  A leaked reader is only reclaimed if the garbage collector happens to
  run and the object is unreachable.  Nothing in the language promises
  that before the limit is hit, which is why the failure looks random.

STUDENT B  -  DESIGN AND CORRECTNESS
================================================================================================================

4.  EVERY RESOURCE THE PROGRAM OPENS, AND WHERE IT MUST BE CLOSED
----------------------------------------------------------------------------------------------------------------
  RESOURCE                 | OPENED WHERE         | MUST CLOSE WHERE         | HOW MANY AT ONCE
  --------------------------------------------------------------------------------------------------------
  BufferedWriter           | start of the report  | after the last store     | 1 for the whole run
  PrintWriter (wraps it)   | same statement       | closing it closes the writer | 1
  FileReader               | top of each store loop | end of THAT iteration    | 1 at a time, f in total if leaked
  BufferedReader (wraps it) | same statement       | closing it closes the FileReader | 1 at a time

  A wrapper owns what it wraps: closing the BufferedReader closes the
  FileReader beneath it, so only the outermost object needs closing.

5.  WHY THE MANUAL VERSION CAN LEAK
----------------------------------------------------------------------------------------------------------------
  Because close() is an ordinary statement, and an exception skips
  ordinary statements.  In the manual version the inner close() sits
  after the parsing loop:

      reader = new BufferedReader(...);
      while ((line = reader.readLine()) != null) { ... parseLong ... }
      reader.close();          <- NEVER REACHED when parseLong throws

  Putting it in a finally fixes THIS leak, but two traps remain:
    (a) if the resource is assigned inside the try, finally must still
        null-check it, because the constructor itself can throw;
    (b) if close() itself throws inside finally, that exception REPLACES
        the original one and the real cause is lost - demonstrated next.

6.  HOW try-with-resources GUARANTEES CLOSING, AND IN WHAT ORDER
----------------------------------------------------------------------------------------------------------------
  Closing order is REVERSE OF DECLARATION, and it happens BEFORE any
  catch or finally attached to the same try. Proof, with three resources:

      opened  first
      opened  second
      opened  third
      body of the try block runs here
      closed  third
      closed  second
      closed  first

  And closing still happens when the body throws:
      opened  outer
      opened  inner
      closed  inner
      closed  outer
      catch clause runs AFTER both closes: body failed

7.  WHAT A SUPPRESSED EXCEPTION IS, AND WHEN IT OCCURS
----------------------------------------------------------------------------------------------------------------
  It occurs when the try body throws AND close() also throws.  Two
  exceptions exist but a method can only throw one, so the one from
  close() is attached to the primary one instead of replacing it.

      primary exception   : java.lang.IllegalStateException: the REAL problem: row 2 of store04 is corrupt
      suppressed          : java.lang.IllegalStateException: close() failed too: disk went offline

  Compare the SAME situation with a manual finally, where close() wins:
      what the caller sees: java.lang.IllegalStateException: close() failed too: disk went offline
      suppressed count    : 0   <- the real cause is GONE

JOINT ENGINEERING DECISION
================================================================================================================
  WHEN IS try-with-resources NOT SUFFICIENT ON ITS OWN?

  CONDITION                                    | WHAT ELSE IS NEEDED
  --------------------------------------------------------------------------------------------------------
  one corrupt row must not abandon the report  | per-row try/catch inside the loop
  the output file is half-written on failure   | write to a temp file, rename on success
  the caller must know WHICH store failed      | logging, or a failure list in the result
  a store file is missing, not corrupt         | a separate catch for IOException per file
  the resource is not AutoCloseable            | a manual finally, or a wrapper that is
  the resource is returned to the caller       | the caller owns closing; TWR would close early
  closing itself must not be silent            | read getSuppressed() and log it
  a lock or a transaction, not a file          | commit/rollback semantics, not just close

  Demonstrated: the robust version, which keeps try-with-resources AND
  adds a per-row catch, on the SAME failing input:
      grand total   : 15600   (all 6 stores reported, not 3)
      rows rejected : 1
          store04.csv line 3: For input string: "SEVEN"
      STORE,ITEMS,TOTAL
      store01.csv,5,3000
      store02.csv,5,3000
      store03.csv,5,3000
      store04.csv,2,600
      store05.csv,5,3000
      store06.csv,5,3000
      TOTAL,,15600

ALTERNATIVE CONCEPT AND COMPLEXITY ANALYSIS
================================================================================================================
  f = number of store files, r = rows per file.

  VERSION                    | TIME           | MAX HANDLES AT FAILURE     | REPORT ON FAILURE
  --------------------------------------------------------------------------------------------------------
  try-with-resources         | O(f x r)       | 1 (the writer only)        | partial, abandoned
  explicit close in finally  | O(f x r)       | 1 (the writer only)        | partial, abandoned
  close after the loop (bug) | O(f x r)       | 2 (writer + the bad reader) | partial, abandoned
  no closing at all          | O(f x r)       | f + 1 - every file ever opened | partial, then crashes
  robust: TWR + per-row catch | O(f x r)       | 1 (the writer only)        | COMPLETE, bad rows listed

  TIME is O(f x r) in every version: each row is read and parsed once,
  and closing a file is O(1).  Resource safety costs nothing in time.

  SPACE is where they differ, and it is not the heap - it is the
  process-wide file-descriptor table, a limit the program shares with
  everything else it does.  With no closing at all the handle count
  grows as O(f), so the program works on a test set of ten stores and
  fails on a chain with a thousand - which is exactly the bug report.

  try-with-resources and a correct finally are EQUIVALENT in both
  columns.  The argument for try-with-resources is not complexity, it is
  that it cannot be got wrong: there is no close() to forget, no
  null-check to omit, and the suppressed exception is kept rather than
  discarded.  Section 7 above shows the manual finally losing the real
  cause of the failure, which no amount of care in the finally recovers.
